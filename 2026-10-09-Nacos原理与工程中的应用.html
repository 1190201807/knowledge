Nacos 原理与工程中的应用 整理日期 2026-10-09 · 应急项目（JeecgBoot 微服务）

一句话总结：Nacos = 服务注册发现 + 配置中心。 前者解决「找谁调」，后者解决「配置放哪」。 我们的生产地址：http://10.240.9.22:8848/nacos/（账号密码默认 nacos / nacos，工程中未配置额外凭据，说明鉴权大概率未开启）。

一、两大职责对比

① 服务注册与发现② 配置中心
解决什么服务之间互相找不到对方地址几十个服务的配置散落各处、改一次要重启一次
怎么工作服务启动时「报到」，调用时「查电话簿」，挂了自动「除名」配置集中存放，启动时拉取，改配置可热推送
类比通讯录 + 实时点名全体服务共用的公共配置文件柜
谁做负载均衡调用方客户端（Nacos 只提供名单，不替你转发流量）—
工程中的体现服务列表页可见 jeecg-task → 172.17.0.10:7003jeecg.yaml 里集中放数据库/Redis/MinIO 生产密码
常见误区纠正：Nacos 本身不做请求转发，它不是网关也不是 Nginx。它只维护一张 「服务名 → 存活实例列表」的表；真正决定调哪个实例的是调用方（Feign/Ribbon 等客户端负载均衡）。

二、职责①：服务注册与发现

完整流程

  • 注册：服务启动后向 Nacos 上报 服务名 + IP:端口；
  • 心跳：定期续约证明自己活着，宕机实例会被自动摘除，流量不再打到坏节点；
  • 发现：调用方按服务名拉取健康实例列表（还会监听变更，实例上下线实时推送）；
  • 调用：调用方在列表里选一个直接请求 —— 这就是「负载均衡在客户端」的含义。

三、职责②：配置中心

工程中的真实接线（jeecg-module-task 为例）

# jeecg-module-task-start/src/main/resources/application.yml
spring:
  application:
    name: jeecg-task                    # ← 注册进 Nacos 用的服务名
  config:
    import:                             # ← 从 Nacos 拉这 4 份配置
      - optional:nacos:jeecg.yaml
      - optional:nacos:jeecg-rabbitmq.yaml
      - optional:nacos:jeecg-dev.yaml
      - optional:nacos:task.properties
  cloud:
    nacos:
      config:
        server-addr: @config.server-addr@   # ← Maven profile 替换，prod 时 = 10.240.9.22:8848
      discovery:
        server-addr: ${spring.cloud.nacos.config.server-addr}
这正是上次找生产 MinIO 配置没找到的原因：仓库里的 application-dev.yml / application-live.yml 只是本地/兜底配置；生产启动时 Nacos 上的 jeecg.yaml 等会覆盖它们。 所以生产的 jeecg.minio.minio_url / minio_name / minio_pass 要登录 Nacos 控制台 → 「配置管理 → 配置列表」→ 打开 jeecg.yaml 查看。

同机其他中间件Redis :16379 · RabbitMQ :5672 · ES :9100（MinIO 不在这台机器，现场为 10.240.9.18:9000）
什么时候需要关心 Nacos？
  • 单体启动（jeecg-system-start 直接跑 application-dev.yml）→ 用不到，Nacos 是微服务/集群部署才必需；
  • 要改生产配置（数据库、Redis、MinIO、MQ 队列名…）→ 去配置中心看；
  • 要排查「服务互相调不通」→ 去服务列表看实例是否注册、是否健康。
