Git Merge vs Rebase 交互式动画教程 —— 一图看懂两条历史线，以及那句神秘的 "Merge branch 'main' of https://xxx.git into main"

口诀：merge 打结不搬家，rebase 搬家不打结；pull 遇分叉自动打结，结上写着那句英文话。

一、核心模型 / 直觉

把提交历史想象成一条时间线地图：每个提交是一个站点，分支是两条岔路。

git merge —— "修一条汇合路"

两条岔路原封不动，只是新建一个汇合站（合并提交），它有两个父节点，把两条路重新连成一体。历史长什么样就保留什么样——一张"铁路图"。

git rebase —— "把我的路拆了，搬到你的路尽头重铺"

把我分支上的提交一个个摘下来，复制一份接到目标分支的最新提交后面。原提交被抛弃（内容一样但哈希变了），历史变成一条直线。

一句话：merge 保留"分叉过"的事实，rebase 伪造"从来没分叉"的历史。

三、公式与边界的推导：为什么 pull 会"自作主张"打结？

git pull 的本质是一个复合命令：

$ git pull  ≡  $ git fetch  +  $ git merge origin/main（或 rebase，见下）

所以 "Merge branch 'main' of https://xxx.git into main" 出现的充要条件可以现场推导出来：

  1. fetch 阶段：把远程仓库（URL = 那个 https://xxx.git）的 main 新提交下载到本地，记为 origin/main。消息里的 'main' of https://xxx.git 就是这么来的——被合并的一方是"远程的 main"。
  2. merge 阶段：Git 把 origin/main 合并进你当前的 main。此时只有两种可能：
    • 你本地没有新提交（只是落后于远程）→ 直接快进（fast-forward），指针往前挪，不产生合并提交；
    • 你本地也有新提交（双方分叉）→ 只能真合并，产生一个合并提交，默认消息就是那句话。

所以判定公式：

本地有未 push 的提交 且 远程也有别人的新提交，此时 git pull → 那句话必然出现在 log 里。

怎么让它永远不出现？

  • 临时：git pull --rebase —— fetch 后改用 rebase，把你的本地提交"搬到"远程提交后面，历史保持直线。
  • 永久：git config --global pull.rebase true —— 以后所有 pull 默认走 rebase。
  • 手动拆开：先 git fetch 看一眼，再自己决定 merge 还是 rebase。

四、对比总结

git mergegit rebase
历史形状铁路图（保留分叉）一条直线（消除分叉）
是否产生新提交是（合并提交，2 个父节点）是（每个原提交的"复制版"，哈希全变）
原提交是否保留保留被抛弃（变成不可达）
冲突处理一次性解决所有冲突可能每个提交都要解一次
是否改写历史否，对已 push 的提交安全是，严禁 rebase 别人可能已拉取的共享分支
典型用途把功能分支合回 main；合成 PR把 main 的最新进展"吸进"自己的私有功能分支；pull 时保持直线

五、口诀

merge 是"修桥"，rebase 是"搬家"；
pull = fetch + 合并，本地远程都动了它就打结；
结上那句英文话 = "把远程的 main 合进我本地的 main"；
pull --rebase 一配，从此只见直线不见结。

六、从零复现的步骤清单

  1. 画两条线：main 和 dev 从同一点分叉，各自有新提交 → 为什么？分叉是讨论 merge/rebase 的前提。
  2. merge 路线：git checkout main && git merge dev → 为什么？产生双父节点的合并提交，两条线都原样保留。
  3. rebase 路线：git checkout dev && git rebase main → 为什么？把 dev 的提交复制到 main 最新提交之后，旧提交变幽灵，哈希全变。
  4. 收尾：rebase 后回 main 执行 git merge dev → 为什么？此时是快进，只挪指针，历史仍是直线。
  5. 解释神秘语句：本地有未 push 提交 + 远程有新提交 + 执行 git pull → 为什么？pull = fetch + merge，fetch 下来的 origin/main 与本地 main 分叉，merge 自动执行，默认消息就是 Merge branch 'main' of <URL> into main。
  6. 根治：git config --global pull.rebase true → 为什么？让 pull 的第二阶段从 merge 换成 rebase，分叉被"搬家"消除，不再打结。
  7. 红线自查：要 rebase 的分支是否已被别人 pull 过？→ 为什么？rebase 改写历史，共享分支被改写会让协作者的历史对不上。
