## 怎么用

- **设计时**：按 1→10 顺序过，把答案写进设计文档或 PR 描述。

## 1. 所有权：这块可变状态归谁？能不能不共享？

**为什么问**
绝大多数并发 bug 来自"多个线程都能改同一块状态，但没人说清谁负责"。先确定所有权，再谈加锁；很多问题在这一步就能消失。

**怎么回答**
- 列出所有可变且被多线程访问的字段、集合、缓存、单例成员。
- 每一项指定唯一的所有者模块（谁能写），其他模块只能读或发消息。
- 依次问：能不能改成不可变？能不能线程封闭（每线程一份/栈上）？能不能用消息传递代替共享？
- 仍然必须共享可变的，才进入第 3–5 问。

**合格答案的样子**
"这个 Map 只由 CacheService 写，其他模块通过它的方法读；内部用 ConcurrentHashMap；不对外暴露原对象。"

**对应阶段**：1–2（不可变、线程封闭）、4（actor/消息传递）

## 2. 不变量：并发下必须永远成立的业务规则是哪几条？

**为什么问**
线程安全的本质是"不变量在并发下不被破坏"。说不出不变量，就不知道锁该包住哪段代码。

**怎么回答**
- 用布尔命题写下业务不变量，例如：库存 ≥ 0；余额 ≥ 0；订单状态只能前进；同一用户同一天只有一条签到；明细之和等于总额。
- 找出哪些代码路径会暂时破坏它，以及破坏期间有没有别的线程能观察到。
- 让临界区/事务覆盖"检查 + 修改"的完整过程。
- 跨行、跨表、跨进程的不变量，优先用数据库约束/事务保证，不要只靠 JVM 锁。

**合格答案的样子**
"扣库存的不变量是 stock >= 0，由一条带 WHERE 的条件更新保证；SELECT 和 UPDATE 之间没有窗口。"

**对应阶段**：1（概念）、2（锁的范围）、4（业务级一致性）

## 3. 原子边界：哪些操作是读-改-写或检查-后-执行？原子性要覆盖到哪一步？

**为什么问**
这是最高频的一类 bug：一行代码不等于一个原子操作。`count++`、先查后插、先判断再扣款，都是复合操作。

**怎么回答**
- 搜索所有读-改-写（`++`、`+=`、基于旧值计算新值）和检查-后-执行（`if (exists)`、`if (stock > 0)`、懒加载）。
- 为每个操作定义原子单元：一次 CAS、一把锁、一条 SQL、一个事务。
- 确认"检查"和"执行"之间没有其他线程插入的窗口。
- 注意：并发容器的单个方法是原子的，但两个方法连起来不是。`map.get` 后再 `map.put` 仍有竞态。

**合格答案的样子**
"用 `UPDATE stock SET n = n - 1 WHERE id = ? AND n >= 1`，影响行数为 0 就失败；而不是先 SELECT 再 UPDATE。"

**对应阶段**：1–2、3（CAS）、4（并发容器）

## 4. 同步手段：锁、原子类、CAS、数据库条件更新/唯一约束，选哪个？为什么？

**为什么问**
选错工具要么留下 bug（该跨进程却用了 JVM 锁），要么制造无谓的竞争（能用原子类却上了大锁）。

**怎么回答**
- 单变量、简单更新 → 原子类；纯统计 → LongAdder。
- 进程内多字段/多对象的复合不变量 → 一把边界清晰的锁。
- 跨进程、需要持久化 → 数据库条件更新、唯一索引、乐观锁版本号、事务；分布式锁是最后手段。
- 读多写少 → 不可变快照、COW、读写锁。
- 写清楚选择理由和代价（竞争、复杂度、失败模式）。

**合格答案的样子**
"进程内用一把锁保护队列和计数的一致性；跨实例的防重靠数据库唯一索引，不靠本地锁。"

**对应阶段**：2–4

## 5. 锁纪律：有几把锁？固定顺序是什么？持锁期间会不会调用外部代码、IO、回调？

**为什么问**
死锁几乎都来自锁顺序不一致或"持锁做别的事"；长临界区还会把并发退化成串行。

**怎么回答**
- 列出所有锁及其保护对象；给锁编号/命名，规定全局获取顺序。
- 持锁期间禁止调用 RPC、DB、发消息、回调、事件监听、可能阻塞的第三方代码。
- 缩小临界区：只包住共享状态的操作，把 IO 和计算移出去。
- 锁对象用 private final 专用对象，不要锁 String/Integer/this，也不要把 this 和 class 混用。
- 能用一把锁解决就别用两把；必须多把时优先 tryLock 带超时。
- 用 `@GuardedBy` / Clang `GUARDED_BY` 标注，让工具检查。

**合格答案的样子**
"全局锁顺序：accountLock(id) 按 id 升序获取；持锁期间只改内存字段，通知和落库都在锁外。"

**对应阶段**：2（核心）、5（死锁排查）

## 6. 等待与超时：所有阻塞是否可超时、可取消？唤醒条件是否在循环里检查？

**为什么问**
永久等待、丢失唤醒、虚假唤醒、关闭时挂死，都是这一问没问导致的。

**怎么回答**
- 每个 `wait` 必须放在 `while (!condition)` 里；优先用 BlockingQueue、CountDownLatch、Condition 等高层工具。
- 所有外部调用、锁获取、`Future.get` 都设置超时。
- 处理中断：捕获 InterruptedException 后恢复中断标志或明确终止，不要吞掉。
- 取消/关闭时能唤醒所有等待者（中断或条件变量广播）。
- 不要把 sleep 当同步手段。

**合格答案的样子**
"消费者在 `while (queue.isEmpty() && !closed)` 里等待；关闭时先置 closed 再唤醒全部；take 有超时。"

**对应阶段**：2（条件变量）、4（阻塞队列/线程池）

## 7. 执行边界：任务进哪个池？队列有界吗？拒绝策略是什么？会不会池内等池？

**为什么问**
线程池是生产事故的高发区：无界队列 OOM、共享池互相拖垮、池内等池造成饥饿死锁。

**怎么回答**
- 盘点所有 Executor：谁创建、谁使用、线程名是什么。
- 按业务隔离线程池；阻塞 IO 和 CPU 密集分开。
- 队列必须有界；线程数和队列容量按压测数据定。
- 拒绝策略显式选择：快速失败、调用方执行、丢弃都要有理由和日志。
- 禁止池内任务同步等待同一池里的另一个任务；需要 fan-out/fan-in 时用独立池或 ForkJoin（注意其中的阻塞）。
- 避免在公共池（parallelStream、CompletableFuture 默认）里跑阻塞任务。
- 每个池都要有关闭策略和第 10 问的指标。

**合格答案的样子**
"订单导出用独立池：核心 4、最大 8、有界队列 200、CallerRuns 并打日志；不在池内等待子任务。"

**对应阶段**：4（核心）、5（监控）

## 8. 上下文与生命周期：ThreadLocal/traceId/事务怎么传播和清理？关闭时在途任务怎么办？

**为什么问**
Web 工程里上下文串号和丢失极其常见；关闭处理不好会丢任务、挂进程、损坏数据。

**怎么回答**
- 列出所有线程上下文：用户身份、租户、MDC/traceId、安全上下文、事务、Locale、请求参数。
- 异步/线程池任务要包装：提交时捕获上下文，执行时恢复，结束后清理。
- ThreadLocal 必须在 finally 里 remove；不要依赖 InheritableThreadLocal 跨线程池传递。
- 事务不要跨线程：异步任务要么独立事务，要么在同一个线程内完成。
- 关闭顺序：停止接收新任务 → 等待在途任务（有超时）→ 强制停止 → 释放资源；注册 shutdown hook。
- 明确哪些线程是 daemon，避免进程无法退出。

**合格答案的样子**
"提交任务时用任务包装（如 TTL 的 TtlRunnable 或自定义装饰器）复制 MDC 和租户；执行完 finally remove；停机时先停入口再 awaitTermination(30s)。"

**对应阶段**：2（ThreadLocal）、4（线程池）、5（运维）

## 9. 顺序与幂等：同一实体的事件会乱序或重复吗？重试安全吗？

**为什么问**
并发消费 + 重试 + at-least-once 消息会让同一实体的事件乱序或重复；这类问题在单机测试里几乎看不出来。

**怎么回答**
- 确定顺序键（orderId、userId、accountId），同一键路由到同一分区/同一消费者/串行执行器。
- 设计幂等：唯一约束、幂等键、状态机前置条件（只能从 A 到 B）、去重表。
- 重试要安全：失败重试不会重复扣款/重复发货。
- 明确消息语义：最多一次、至少一次、恰好一次，以及业务能否接受重复。
- 并发写同一行数据时，考虑版本号/条件更新，避免后写覆盖先写。

**合格答案的样子**
"同一 orderId 按 hash 进同一队列，单线程消费；创建订单用唯一索引防重，支付回调按状态机幂等。"

**对应阶段**：4（并发模式），并与分布式一致性衔接

## 10. 可观测性：出问题时看哪些指标能定位？

**为什么问**
并发 bug 概率低、难复现；没有指标和日志，只能靠猜。

**怎么回答**
- 指标：线程数、线程池 active/queue/rejection、任务耗时分布、锁等待时间、错误率、超时数。
- 日志：线程名、traceId、关键状态变更前后值；日志本身避免同步锁竞争。
- 排障工具：jstack/线程 dump、pstack、async-profiler、perf；能一键拿到。
- 测试：race detector/TSan 进 CI，压测和故障注入常规化。
- 告警：队列持续增长、拒绝数上升、线程数异常、任务延迟超阈值。

**合格答案的样子**
"每个池暴露 active/queue/rejected 指标；队列 > 80% 或拒绝 > 0 告警；事故时先抓线程 dump。"

**对应阶段**：5
