## 1. 总公式

**线程安全问题 = 共享的可变状态 × 并发访问 × 缺少同步**

三个因子任意去掉一个，问题就不存在：

- 不共享（每线程一份、进程隔离、消息传递）→ 安全
- 不可变（只读、final/const、每次返回新对象）→ 安全
- 共享可变，但有正确的同步 → 安全

后面学的锁、原子类、线程池、actor，本质上都在消掉其中一个因子。判断一段代码有没有风险，先套这个公式。

补充一个定义：**线程安全**是指多线程访问时，不需要调用方额外同步，代码仍然表现正确——不变量不被破坏、不丢更新、读不到半成品状态、不崩溃。

## 2. 进程、线程与内存布局

- **进程**是资源分配和隔离的单位：独立地址空间、文件描述符、信号处理等。
- **线程**是 CPU 调度的单位：共享进程的堆、代码段、静态区，但有自己的栈、寄存器和程序计数器。
- **一次上下文切换**：保存当前线程的寄存器、PC、栈指针，恢复另一个线程的；切换进程还要换页表，TLB 和缓存会受影响。开销通常在微秒级，但会污染缓存，所以线程不是越多越好。
- **并发不等于并行**：单核上线程交替执行也能产生所有并发 bug；多核只是让"同时发生"成为现实，并让可见性问题更复杂。

一个进程大致是这样：

```text
进程
├─ 代码段                 共享
├─ 堆                     共享   ← new 出来的对象、成员变量
├─ 静态/全局区             共享   ← static 字段、全局变量
├─ 线程 A：栈 + 寄存器 + PC   私有
└─ 线程 B：栈 + 寄存器 + PC   私有
```

由此得到一条非常实用的判断规则：

```java
class Counter {
    private int count;          // 堆上的共享状态

    void add() {
        int step = 1;           // 栈上的局部变量，线程私有
        count = count + step;   // 读的却是共享字段
    }
}
```

`step` 是安全的，`count` 不安全。**看到一个变量，先问它在栈上还是堆/静态区，有没有别的线程能拿到它。** 局部变量如果引用了一个共享对象，改它的字段依然不安全——栈私有的是"引用"本身，不是引用指向的对象。

## 3. 原子性：一行代码不是一步

`count++` 概念上是三步（Java 字节码大致是 `getfield` → `iconst_1` → `iadd` → `putfield`）：

```text
读 count  →  加 1  →  写回 count
```

两个线程可以这样交错：

| 时刻 | 线程 A       | 线程 B       | count |
| ---- | ------------ | ------------ | ----- |
| t1   | 读 count = 0 |              | 0     |
| t2   |              | 读 count = 0 | 0     |
| t3   | 计算 0 + 1   |              | 0     |
| t4   |              | 计算 0 + 1   | 0     |
| t5   | 写 count = 1 |              | 1     |
| t6   |              | 写 count = 1 | 1     |

两次 `++`，结果只加了 1。这就是**丢失更新**。

**原子操作**是指不可分割、其他线程看不到中间状态的操作。常见的非原子操作：

- `count++`、`count += n`、`flag = !flag`
- `if (map.get(k) == null) map.put(k, v)`（检查-后-执行）
- `if (stock > 0) stock--`
- 非线程安全集合上的 `add`（内部可能扩容、改 size）
- "先遍历再修改"这类复合操作

常见的原子操作：

- 大多数单个基本类型的读写（但仍有可见性问题；另外 Java 中非 volatile 的 `long`/`double` 在部分平台上可能被拆成两次写，不保证原子性）
- 原子类的方法，比如 `incrementAndGet`
- 锁保护的临界区
- 数据库的一条条件更新或一个事务

这里有个非常重要的区分：**"单个方法是原子的"不等于"多个方法组合起来是原子的"。** `ConcurrentHashMap` 的每个方法都安全，但 `get` 完再 `put`，中间仍然有窗口。

## 4. 可见性：写进去不等于看得见

看这段代码：

```java
class Worker {
    private boolean stop = false;   // 没有 volatile

    void run() {
        while (!stop) {
            // 空转
        }
        System.out.println("exit");
    }

    void shutdown() {
        stop = true;
    }
}
```

线程 A 跑 `run()`，线程 B 调 `shutdown()`，A 可能永远不退出。原因不止一个：

- JIT 可能把 `stop` 读进寄存器，循环里不再重新读内存。
- CPU 可能从自己的缓存读旧值。
- 编译器可能认为 `stop` 不会被别的线程修改，从而做更激进的优化。

关键理解：**这不是"写没写进去"的问题，而是"另一个线程什么时候、是否被允许看到"的问题。** 硬件缓存一致性（MESI 之类）保证缓存行最终一致，但语言层面的可见性还需要同步机制来约束编译器和 CPU。硬件行为不能作为程序正确性的依据。

所以会出现一种很坑的现象：**在 x86 上跑对了，换个 JDK 版本、换个 CPU、换个优化级别就错了。** 也可能你在循环里加一句 `System.out.println` 就"好了"——那是因为 `println` 内部有同步，属于碰巧，不是修复。

Java 的修复是给 `stop` 加 `volatile`；C++ 用 `std::atomic<bool>`（注意 C++ 的 `volatile` 不提供线程间同步语义）；Go 用 `atomic.Bool` 或 channel。加锁也能解决可见性。

## 5. 有序性：你写的顺序不等于执行顺序

编译器和 CPU 会在不改变**单线程**语义的前提下重排指令，这叫 as-if-serial。问题在于：它们只保证单线程看起来没变，**不保证其他线程看到的顺序和源码一致**。

```java
// 线程 A
data = 42;
ready = true;

// 线程 B
if (ready) {
    System.out.println(data);  // 可能打印 0
}
```

A 的两条写可能被重排，B 可能先看到 `ready = true`，再看到还没赋值的 `data`。

经典的双检锁单例是同一个问题：

```java
class Singleton {
    private static Singleton instance;   // 缺少 volatile

    static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查，在锁外
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();    // 分配、初始化、赋值，可能重排
                }
            }
        }
        return instance;
    }
}
```

`new Singleton()` 可以拆成三步：分配内存、初始化字段、把引用赋给 `instance`。后两步可能重排。另一个线程在第一次检查时看到 `instance != null`，就会拿到一个**还没初始化完的对象**。修复是 `private static volatile Singleton instance;`——`volatile` 禁止相关重排并保证可见性。

有序性问题的可怕之处在于：**代码看起来加锁了，但第一次检查在锁外，锁保护不到它。**

## 6. 三类问题对照

| 问题   | 你会观察到什么                 | 典型例子                | 解决手段                       |
| ------ | ------------------------------ | ----------------------- | ------------------------------ |
| 原子性 | 丢失更新、重复创建、超卖       | `count++`、检查-后-执行 | 锁、原子类/CAS、事务、条件更新 |
| 可见性 | 读不到最新值、循环不退出       | 非 volatile 停止标志    | volatile、锁、原子变量         |
| 有序性 | 看到半初始化对象、依赖顺序错乱 | 双检锁、初始化发布      | volatile、锁、内存屏障         |

两个考试常考、工程也常错的点：

- **锁可以同时解决三者**：互斥保证原子性，锁的释放/获取建立可见性和顺序保证。
- **volatile 只解决可见性和有序性，不解决复合操作的原子性**。`volatile int count; count++;` 依然会丢更新。

## 7. 竞态条件 vs 数据竞争

这两个词经常混用，但含义不同：

- **竞态条件（race condition）**：程序的正确性依赖于线程执行的时序。范围更大，是业务视角。
- **数据竞争（data race）**：形式化定义——两个线程访问同一内存位置，至少一个是写，且没有 happens-before 关系。是工具能检测的那一类。

几个例子帮助区分：

- `ConcurrentHashMap` 上先 `get` 再 `put`：**没有数据竞争**（每个方法都做了同步），但**有竞态条件**（可能重复创建）。
- `volatile int count; count++`：在 Java 内存模型下**没有数据竞争**（volatile 访问之间有顺序），但**有竞态条件**（丢失更新）。
- 两个线程同时写一个普通 `int` 字段：**既是数据竞争，也是竞态条件**。

**补充：happens-before 是什么**

happens-before（HB）读作"已发生且对后者可见"比字面直译准确：它不是墙上时钟的先后，而是语言给的一条**可见性承诺**——A HB B 表示 A 写的数据对 B 可见，且实现不能让 B 表现得像发生在 A 之前。反过来，**没有 HB 关系的两个冲突访问，语言什么都不保证**（读可能看到旧值、可能被重排），数据竞争的定义就建立在"没有 HB"上。HB 只管可见性和顺序，**不管互斥和原子性**。

HB 边的来源（记住前两条就够用）：

1. **同一线程的程序顺序**：线程内前面的操作 HB 后面的操作。
2. **同步动作配对**：volatile 写 → 同步顺序（语言给所有同步动作排的一条全序，不是物理时钟）中之后的同变量 volatile 读；读在写之前则不适用，它看到的是前面最近一次写。另有：解锁 → 之后同一把锁的加锁；`start` → 线程首动作；线程末动作 → `join` 返回。
3. **传递性**：A HB B、B HB C ⇒ A HB C。

```java
// 线程 A
data = 42;        // ① 普通写
flag = true;      // ② volatile 写

// 线程 B
if (flag) {       // ③ volatile 读，读到 true
    print(data);  // ④ 一定打印 42
}
```

①→②、③→④ 是程序顺序，②→③ 是 volatile 规则，传递得 ① HB ④。第 5 节那个不加 volatile 的 `data = 42; ready = true;` 缺的就是 ②→③ 这条边。

**为什么 `volatile count++` 没有数据竞争、却有竞态条件**

`count++` 在 JMM 层面是三个动作：**volatile 读 → 加 1 → volatile 写**。每一次访问都被同步顺序管着，每次读看到的值是唯一确定的，不存在"没有 HB 约束的冲突访问"——**没有数据竞争**。

但看这个交错：

| 时刻 | 线程 A          | 线程 B          | count |
| ---- | --------------- | --------------- | ----- |
| t1   | volatile 读 → 5 |                 | 5     |
| t2   |                 | volatile 读 → 5 | 5     |
| t3   | 算出 6          |                 | 5     |
| t4   |                 | 算出 6          | 5     |
| t5   | volatile 写 6   |                 | 6     |
| t6   |                 | volatile 写 6   | 6     |

这个执行满足了所有 HB 承诺（每次读都看到当时最新的值），内存模型层面完全合法，业务上却丢了一次更新。因为 **HB 只承诺"每个读看到哪个写"，不承诺"读-改-写作为整体不被打断"**：A 的读和写之间有 HB，但 B 的整个读-改-写可以从中间合法地穿过去。

一句话：**HB 管"看得到"，锁管"碰不到"。** 要消灭丢更新得换 `AtomicInteger.incrementAndGet`（CAS）或 `synchronized`（互斥）——它们提供的是原子性，volatile 没有。

**volatile 小结**

- **可见性**：volatile 变量的写，对同步顺序中后续的读保证可见（读一定看到这次写或更新的写）。JIT 不能把读缓存在寄存器里、不能提升出循环、不能消除写。
- **有序性**：volatile 写是释放屏障（volatile 写操作前的指令不能重排到写操作之后）；volatile 读是获取屏障（volatile 读操作后的指令不能重排到读操作之前）。编译器屏障和 CPU 内存屏障两层都管。
- **建立 happens-before**：volatile 写 HB 后续同变量读，能把写在前面的数据一起"捎带发布"（release/acquire 配对），这是 DCL 和安全发布的基础。
- **单次访问的原子性**：单次 volatile 读/写不可分割（Java 的 volatile `long`/`double` 不会撕裂）。
- **不保证复合操作的原子性**：`count++` 是读-改-写三步，仍然丢更新，要用原子类/CAS 或锁。
- **不提供互斥**：挡不住其他线程在"读"和"写"之间插进来。
- **适用边界**：一个写者、写完发布、多个读者只读的标志位场景；需要互斥或多写者时用锁/原子类。
- **表述提醒**：不要用"volatile 绕过缓存、直接读写主内存"来解释——物理上 CPU 照样走缓存，保证来自编译器和 CPU 的屏障以及缓存一致性协议，"绕过缓存"只是简化模型，不能作为正确性依据（见第 4 节）。

不同语言的后果不同：C++/Rust 里数据竞争是未定义行为，什么都可能发生；Java 没有 C++ 意义上的 UB，但可能读到旧值、看到不一致的状态；Go 有 race detector 帮你抓。后面阶段 5 会专门学工具，这里先记住：**工具抓的是数据竞争，业务怕的是竞态条件，两者不能互相替代。**

> 跨语言提醒：C++ 的 `volatile` 不建立 happens-before，所以并发 `volatile count++` 在 C++ 里仍然是数据竞争（且是 UB）；不要把它和 Java 的 `volatile` 混为一谈。

## 8. 死锁的四个必要条件

```java
void transfer(Account from, Account to, int amount) {
    synchronized (from) {
        synchronized (to) {
            from.balance -= amount;
            to.balance += amount;
        }
    }
}
```

线程 1 执行 `transfer(A, B)`，线程 2 执行 `transfer(B, A)`：一个持有 A 等 B，一个持有 B 等 A，死锁。

死锁发生必须同时满足四个条件：

1. **互斥**：资源一次只能被一个线程持有。
2. **持有并等待**：持有资源的同时等待其他资源。
3. **不可剥夺**：不能强行把资源抢走。
4. **循环等待**：存在一个等待环。

破坏任意一个就能避免死锁：

- 固定加锁顺序（比如按账户 id 排序）→ 破坏循环等待
- `tryLock` 带超时 → 主动放弃已持有的锁，破坏持有并等待/不可剥夺
- 一次性申请所有锁 → 破坏持有并等待
- 把多个资源的操作合并到一个临界区、只保留一把锁 → 从结构上消灭循环等待

顺便区分：死锁是**活跃性**问题，程序没算错数据，只是不往前走了；数据错乱是**安全性**问题。后面还会遇到活锁和饥饿，先知道这三个词的方向即可。

## 9. 总心法：所有解法只有四类

1. **不共享**：线程封闭、每线程一份、进程隔离、消息传递
2. **共享但不可变**：final/const、不可变对象、每次返回新副本
3. **共享可变 + 互斥**：锁、事务内存
4. **共享可变 + 原子操作**：CAS、原子变量、数据库条件更新

遇到任何并发问题，先问自己：我现在用的是哪一类？如果一类都不是，那就是 bug 的温床。

## 10. 必做实验

不用写得很复杂，重点是**亲眼看到 bug**，并记录"现象 → 复现条件 → 根因 → 修复 → 验证"。

1. **丢失更新**：两个线程各对同一个 `int` 累加 10 万次，用 `CountDownLatch` 让它们同时开始，打印最终值。多跑几次，观察结果小于 20 万。
2. **可见性**：线程 A 空转 `while (!stop)`，线程 B 睡 1 秒后把 `stop` 置 true。先不加 `volatile`，看 A 是否退出；再加 `volatile` 对比。注意：不加 volatile 时也可能退出，这本身就是重要一课——并发 bug 是概率性的，不能靠"没复现"证明正确。
3. **转账死锁**：两个账户、两个线程反方向转账，在 `synchronized` 里 `sleep` 一下放大窗口。用 `jstack <pid>` 看 "Found one Java-level deadlock" 和 BLOCKED 线程；C++ 用 `pstack`/gdb。
4. **错误版生产者-消费者**：用 `if` 而不是 `while` 等条件，或者先 `notify` 再 `wait`，观察丢失唤醒或条件不成立却继续执行。这个实验会直接把你带到阶段 2 的条件变量。

C++ 的话，把 `synchronized` 换成 `std::mutex` + `std::lock_guard`，用 TSan 编译跑一遍；Go 用 `go run -race`。原理完全一样。

## 11. 常见误区

- "加了锁就安全"——锁要保护正确的不变量，而且所有访问路径必须用同一把锁。
- "用了 volatile 就安全"——它不保证 `count++` 的原子性。
- "用了 ConcurrentHashMap 就安全"——复合操作仍然有竞态。
- "单线程测试通过就行"——并发 bug 是概率性的。
- "线程越多越快"——上下文切换、锁竞争、缓存失效都会反噬。
- "sleep 一下就能保证顺序"——sleep 不是同步，只是让 bug 更难复现。

学完后先不看讲义，自己写一遍答案；然后再让我在对话里提问。

### 1. 进程和线程的区别？一次上下文切换发生了什么？

我的答案：

- **进程**是资源分配和隔离的基本单位：独立地址空间（页表）、文件描述符、信号处理等。**线程**是 CPU 调度的基本单位：共享进程的堆、代码段、静态区、文件描述符，私有的只有栈、寄存器（含 PC、栈指针）和线程局部存储。
- **一次上下文切换**：进入内核，把当前执行流的寄存器、PC、栈指针等上下文保存到它的 TCB（进程则是 PCB），再从另一个 TCB 恢复；切换进程还要切换地址空间（换页表基址），代价是 TLB 失效/刷新、缓存和分支预测的局部性被破坏。切线程不换地址空间，所以更便宜；但两者都是微秒级且有缓存污染，所以线程不是越多越好。
- 补充：**并发不等于并行**，单核上线程交替执行也能产生所有并发 bug。

### 2. 竞态条件和数据竞争有什么区别？

我的答案：

- **数据竞争**是数据/内存模型层的形式化概念：两个线程访问同一内存位置，至少一个是写，且两者之间没有 happens-before 关系。这时语言不保证读到什么；工具（TSan、Go `-race`）能直接检测的就是它；C++/Rust 里是未定义行为。
- **竞态条件**是业务/逻辑层的概念：只要正确性依赖于线程交错的具体时序，就是竞态条件，哪怕每次访问都同步好了。
- 例子：`volatile int count; count++` **不构成数据竞争**（每次 volatile 访问都被同步顺序管住，每次读看到的值唯一确定），但**有竞态条件**（读-改-写非原子，两个线程从同一旧值出发，后写覆盖先写，丢更新）。
- 反方向也不重合（存在不造成业务错误的良性数据竞争），所以**工具抓数据竞争，业务怕竞态条件**，"没检测到数据竞争"推不出"没有竞态条件"。

### 3. 原子性、可见性、有序性分别会导致什么 bug？

我的答案：

- **原子性**：操作不可分割、其他线程看不到中间状态。典型 bug：丢失更新、超卖、重复创建（检查-后-执行、读-改-写）。修复：锁、原子类/CAS、数据库条件更新/事务。
- **可见性**：一个线程的写，另一个线程**是否、何时被允许看到**——不是"及不及时"，而是语言是否承诺。没有同步时读可能一直用寄存器/缓存里的旧值，JIT 甚至可能把读提升到循环外。典型 bug：读到旧值、`while (!stop)` 循环不退出。修复：volatile、锁、原子变量。
- **有序性**：编译器和 CPU 在 as-if-serial 前提下重排，单线程语义不变，但不保证其他线程看到的顺序。典型 bug：发布模式看到 `flag = true` 却读到旧 `data`；DCL 拿到半初始化对象。修复：volatile（禁止相关重排、建立 HB）、锁（双方必须用同一把锁）、内存屏障。
- 汇总：**锁三样都管；volatile 只管可见性和有序性**，不解决复合操作的原子性。

### 4. 死锁的四个必要条件是什么？

我的答案：

- 四个条件：**互斥**（资源一次只能被一个线程持有）、**持有并等待**（拿着一把等另一把）、**不可剥夺**（不能强行抢走）、**循环等待**（等待关系成环）。四者必须同时满足，破坏任意一个即可。
- 转账 A→B、B→A 的例子：按固定顺序加锁（比如按账户 id 排序，所有线程都先锁小 id），等待关系无环 → **破坏循环等待**。
- 其他破坏手段：`tryLock` 带超时、拿不到就主动放弃已持有的锁 → 破坏持有并等待/不可剥夺；一次性申请全部锁 → 破坏持有并等待；多资源合并成一把锁、一个临界区 → 从结构上消灭循环等待。
- 补充：死锁是**活跃性**问题（数据没算错，只是不往前走了），数据错乱是**安全性**问题，两者要分开。

---

## 本讲小结

如果只能带走 8 句话：

1. 线程安全问题的土壤是"共享的可变状态"。
2. 一行代码不是一步，`count++` 是读-改-写。
3. 局部变量线程私有，共享对象的字段不是。
4. 可见性问的是"另一个线程是否、何时能看到"，不是"有没有写进去"。
5. 有序性问题来自编译器和 CPU 在单线程语义下重排。
6. `volatile` 管可见性和有序性，不管复合操作的原子性；锁三者都管。
7. 竞态条件看业务正确性，数据竞争看 happens-before，工具只能直接抓后者。
8. 死锁四条件：互斥、持有并等待、不可剥夺、循环等待，破坏任意一个即可。
