## 1. 这一阶段在解决什么

阶段 0–1 你知道了三件事：

- 并发 bug 来自共享可变状态 + 并发访问 + 缺少同步。
- 缺少同步会以原子性、可见性、有序性三种方式失效。
- 死锁需要四个条件同时成立。

阶段 2 要回答的是：**用什么工具、按什么规则，把“缺少同步”补上，同时不引入死锁和活性问题。**

同步原语不是“越多越好”的护身符，而是一组契约：

| 原语            | 提供的保证                       | 典型用途                | 代价                     |
| --------------- | -------------------------------- | ----------------------- | ------------------------ |
| 互斥锁          | 临界区互斥；可见性；有序性       | 保护多变量/复合不变量   | 竞争、串行化、死锁风险   |
| 条件变量        | 在锁的保护下等待条件             | 生产者-消费者、等待状态 | 使用复杂，易丢失唤醒     |
| 信号量          | 许可计数；限制并发               | 限流、资源池            | 许可泄漏、公平性         |
| 原子类/CAS      | 单变量读改写原子；可见性；有序性 | 计数器、标志、状态机    | 高竞争下自旋；多变量不够 |
| 读写锁          | 读读并发、读写互斥               | 读多写少                | 写饥饿、开销             |
| 不可变/线程封闭 | 从根上消除共享可变               | DTO、配置、上下文       | 需要设计约束             |

一句话：**锁解决“互斥”，条件变量解决“等待”，信号量解决“限量”，原子类解决“单点更新”。** 先想清楚要解决哪个问题，再选工具。

## 2. 互斥锁：语义、家族与选择

### 2.1 锁的核心语义

- **acquire（加锁）**：如果锁空闲，获得锁；否则阻塞/自旋/失败。
- **release（解锁）**：释放锁，唤醒等待者。
- **互斥**：同一时刻只有一个线程持有。
- **所有权**：多数锁要求“谁加锁谁解锁”；Java 的 `synchronized` 在异常时自动释放，C++ 的 `std::mutex` 不是。
- **可重入性**：同一线程能否重复加锁。Java 的 `synchronized`/`ReentrantLock` 可重入；C++ `std::mutex`、Go `sync.Mutex` 不可重入。
- **公平性**：公平锁按等待顺序授予；非公平锁允许插队，吞吐更高但可能饥饿。

> C++ 的 `std::mutex` 如果由非持有线程解锁，是未定义行为；Go 的 `sync.Mutex` 也不绑定所有者，但解锁未持有的锁会 panic。不要依赖“任何线程都能解锁”的错觉。

### 2.2 Java 的锁家族

| 锁                       | 特点                                                             | 适用                         |
| ------------------------ | ---------------------------------------------------------------- | ---------------------------- |
| `synchronized`           | JVM 内置监视器；可重入；异常自动释放；不能超时/中断              | 大多数简单场景               |
| `ReentrantLock`          | 可重入；`tryLock`、`lockInterruptibly`、公平锁、多个 `Condition` | 需要超时、可中断、多条件队列 |
| `ReentrantReadWriteLock` | 读读共享、读写互斥；可公平/非公平                                | 读多写少，且读操作较长       |
| `StampedLock`            | 乐观读、悲观读、写锁；不可重入                                   | 读极多、写极少，能接受复杂性 |

`synchronized` 的锁对象：

- 实例方法锁 `this`。
- 静态方法锁 `Class` 对象。
- 代码块锁括号里的对象。
- 三者不是同一把锁，混用不会互斥。

```java
class Counter {
    private int count;

    synchronized void inc() { count++; }          // 锁 this
    static synchronized void reset() { }           // 锁 Counter.class
}

// 等价于
void inc() {
    synchronized (this) { count++; }
}
```

`ReentrantLock` 的标准写法：

```java
private final ReentrantLock lock = new ReentrantLock();

void inc() {
    lock.lock();
    try {
        count++;
    } finally {
        lock.unlock();
    }
}
```

一定要 `try/finally`，否则异常路径会永久持锁。

### 2.3 C++ 的锁家族

| 锁                     | 特点                                   |
| ---------------------- | -------------------------------------- |
| `std::mutex`           | 基本互斥，不可重入                     |
| `std::recursive_mutex` | 可重入，通常不推荐（容易掩盖设计问题） |
| `std::timed_mutex`     | 支持 `try_lock_for/until`              |
| `std::shared_mutex`    | 读写锁（C++17）                        |

RAII 包装：

```cpp
std::mutex m;
int count = 0;

void inc() {
    std::lock_guard<std::mutex> lk(m);   // 构造加锁，析构解锁
    ++count;
}

// 需要中途解锁/重新加锁/条件变量时用 unique_lock
std::unique_lock<std::mutex> lk(m);
lk.unlock();
lk.lock();
```

多把锁用 `std::scoped_lock`（C++17）或 `std::lock` 一次性加锁，避免顺序死锁：

```cpp
std::scoped_lock lk(m1, m2);   // 内部使用死锁避免算法
```

### 2.4 Go 的锁

```go
var mu sync.Mutex
var count int

func inc() {
    mu.Lock()
    defer mu.Unlock()   // 异常/return 都能解锁
    count++
}
```

Go 的 `sync.Mutex` 不可重入；`sync.RWMutex` 提供读写锁。Go 的哲学更偏向 channel/消息传递，但锁在保护小状态时仍然常用。

### 2.5 怎么选

- 默认用最简单的：Java `synchronized`、C++ `lock_guard`、Go `defer Unlock`。
- 需要 `tryLock`、超时、可中断、公平、多个条件队列 → `ReentrantLock` / `unique_lock` + `condition_variable`。
- 读多写少，且临界区不短 → 读写锁；但先测量，读写锁不一定更快。
- 不要为了“显得高级”上 `StampedLock`/无锁；复杂度和维护成本是真实成本。

## 3. 锁到底保护什么：不变量与临界区

这是阶段 2 最重要的一句话：**锁保护的不是变量，而是不变量。**

### 3.1 什么是不变量

不变量是“在任何可被其他线程观察到的时刻都必须成立的条件”。例如：

- 转账：所有账户余额之和不变；任何账户余额 ≥ 0。
- 有界队列：`0 <= size <= capacity`；`head/tail/size` 三者一致。
- 缓存：`map.size()` 与 `size` 字段一致；key 存在时 value 非空。
- 状态机：订单状态只能从 `CREATED` → `PAID` → `SHIPPED`，不能回退。

写并发代码前，先用一句话写下不变量。写不出来，说明你还没想清楚要保护什么。

### 3.2 临界区要覆盖完整操作

不变量通常由多个步骤共同维护，临界区必须覆盖这些步骤：

```java
// 错误：检查在锁外
if (map.get(k) == null) {
    synchronized (lock) {
        map.put(k, v);
    }
}

// 正确：检查和修改在同一个临界区
synchronized (lock) {
    if (map.get(k) == null) {
        map.put(k, v);
    }
}
```

```java
// 错误：两次余额修改不在同一个临界区
synchronized (from) { from.balance -= amount; }
synchronized (to)   { to.balance += amount; }

// 正确：要么同一把锁，要么按顺序持有两把锁并覆盖整个转账
synchronized (lock) {
    from.balance -= amount;
    to.balance += amount;
}
```

### 3.3 锁粒度

- **太粗**：一个全局锁保护所有状态，所有请求排队，吞吐下降，锁竞争成为瓶颈。
- **太细**：锁只包住一部分操作，不变量被破坏；或者多把锁带来死锁风险。
- **合适**：锁覆盖维护同一不变量的最小代码段；不包含 I/O、RPC、回调、长计算。

经验：**先粗后细**。先用一把边界清晰的锁保证正确，压测发现竞争后再拆分；拆分前先确认不变量是否可以独立。

### 3.4 一把锁保护一个不变量

- 如果一把锁保护多个不相关的不变量，考虑拆分（但拆分后要重新检查跨不变量的操作）。
- 如果一个不变量需要多把锁才能保护，说明设计有问题：要么合并锁，要么用更高层的组件封装。
- 用 `@GuardedBy("lock")` 或注释写清楚“这个字段由哪把锁保护”。

## 4. 条件变量：等待-通知的正确姿势

### 4.1 为什么需要条件变量

只有锁时，等待一个条件成立有两种笨办法：

- 忙等：`while (!condition) { }` —— 浪费 CPU，还持有锁，其他线程进不来。
- `sleep` 轮询：延迟不可控，可能错过状态变化。

条件变量解决的是：**在锁的保护下，原子地释放锁并睡眠，直到被唤醒后重新加锁。** 它让“检查条件”和“进入等待”成为一个不可分割的动作，避免丢失唤醒。

### 4.2 标准协议

```java
synchronized (lock) {
    while (!condition) {   // 必须是 while
        lock.wait();       // 原子地释放锁并等待；返回前重新加锁
    }
    // 条件成立，执行操作
}

// 另一个线程
synchronized (lock) {
    // 修改状态，使 condition 成立
    lock.notifyAll();      // 通知等待者
}
```

C++ 的等价写法：

```cpp
std::unique_lock<std::mutex> lk(m);
cv.wait(lk, [&]{ return condition; });   // 内部就是 while 循环
// ...
cv.notify_one();   // 或 notify_all()
```

Go：

```go
mu.Lock()
for !condition {
    cond.Wait()   // 内部释放 mu 并等待，返回前重新加锁
}
// ...
cond.Signal()    // 或 Broadcast()
mu.Unlock()
```

### 4.3 为什么必须是 while，不能是 if

四个原因：

1. **虚假唤醒（spurious wakeup）**：操作系统/JVM 允许 `wait` 在没有 `notify` 的情况下返回。醒来后条件可能仍不成立。
2. **多个等待者、不同谓词**：`notifyAll` 会唤醒所有等待者，但只有一部分人的条件成立；其他人必须重新检查并继续等。
3. **唤醒后锁可能被抢**：从被唤醒到重新拿到锁之间，另一个线程可能已经改变了状态，条件再次不成立。
4. **丢失唤醒的兜底**：即使 notify 发生在 wait 之前，`while` 也能在进入等待前发现条件已成立，从而不睡。

一句话：**`wait` 返回只代表“可能有机会了”，不代表“条件成立了”。** 条件必须重新检查。

### 4.4 为什么 notify 要在状态修改之后

错误顺序：

```java
// 线程 A：先通知，后改状态
lock.notifyAll();
condition = true;
```

线程 B 被唤醒，重新拿到锁，检查 `condition` 发现还是 false，继续睡；等 A 改完状态，可能再也没有 notify，B 永久等待。这叫**丢失唤醒**。

正确顺序：

```java
synchronized (lock) {
    condition = true;
    lock.notifyAll();
}
```

先改状态，再通知。Java 的 `notify/notifyAll` 必须在持有同一监视器时调用；C++ 的 `notify_one/notify_all` 可以在解锁后调用（常见优化），但状态修改必须在锁内，且要保证等待者能看到新状态。

### 4.5 notify vs notifyAll

- `notify` 只唤醒一个等待者。如果所有等待者等待的是**同一个谓词**，且一个唤醒就够，可以用 `notify`。
- 如果等待者等待**不同谓词**（生产者等“不满”、消费者等“不空”），用 `notify` 可能唤醒错的人，导致该走的人没走、不该走的人醒了又睡，甚至永久等待。此时用 `notifyAll`，或者用两个条件变量。
- 用两个 `Condition`（Java）或两个 `condition_variable`（C++）可以精确唤醒，减少无效唤醒：

```java
ReentrantLock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();
Condition notEmpty = lock.newCondition();
```

### 4.6 有界阻塞队列：标准实现

Java 版（`wait/notifyAll`）：

```java
class BoundedQueue<T> {
    private final Object lock = new Object();
    private final Object[] items;
    private int head, tail, size;

    BoundedQueue(int capacity) {
        items = new Object[capacity];
    }

    void put(T x) throws InterruptedException {
        synchronized (lock) {
            while (size == items.length) {
                lock.wait();
            }
            items[tail] = x;
            tail = (tail + 1) % items.length;
            size++;
            lock.notifyAll();
        }
    }

    @SuppressWarnings("unchecked")
    T take() throws InterruptedException {
        synchronized (lock) {
            while (size == 0) {
                lock.wait();
            }
            T x = (T) items[head];
            items[head] = null;
            head = (head + 1) % items.length;
            size--;
            lock.notifyAll();
            return x;
        }
    }
}
```

要点：

- `while` 检查条件。
- 状态修改和 `notifyAll` 在同一个临界区。
- `take` 取出后把槽位置空，避免内存泄漏。
- 处理 `InterruptedException`：要么向上抛，要么恢复中断标志。

C++ 版（两个条件变量 + 谓词）：

```cpp
template <typename T>
class BoundedQueue {
    std::mutex m;
    std::condition_variable not_full, not_empty;
    std::deque<T> q;
    size_t cap;

public:
    explicit BoundedQueue(size_t capacity) : cap(capacity) {}

    void put(T x) {
        std::unique_lock<std::mutex> lk(m);
        not_full.wait(lk, [&]{ return q.size() < cap; });
        q.push_back(std::move(x));
        lk.unlock();
        not_empty.notify_one();
    }

    T take() {
        std::unique_lock<std::mutex> lk(m);
        not_empty.wait(lk, [&]{ return !q.empty(); });
        T x = std::move(q.front());
        q.pop_front();
        lk.unlock();
        not_full.notify_one();
        return x;
    }
};
```

要点：

- `wait(lock, pred)` 自动处理虚假唤醒。
- 两个条件变量分别对应“不满”和“不空”，避免 `notify_all` 的惊群。
- 解锁后再 `notify` 是常见优化：被唤醒的线程不必先等锁。

### 4.7 条件变量的常见 bug 与误用

- 用 `if` 而不是 `while`。
- 先 `notify` 后改状态。
- `wait` 和 `notify` 用了不同的锁对象。
- 改了状态但忘记 `notify`。
- 多个谓词共用一个条件变量，却用 `notify`。
- 在 `wait` 返回后做长耗时操作，仍持有锁（严格说是锁纪律/性能陷阱；若长耗时操作依赖其他线程拿同一把锁，会升级为死锁）。
- 忘记处理中断/取消。

### 4.8 wait 返回后，锁还在手里

Java 的 `wait()`、C++ 的 `condition_variable::wait()`、Go 的 `Cond.Wait()` 都有一个共同语义：**等待时释放锁，返回前重新加锁**。所以 `wait` 返回后的代码，仍然在临界区里。

常见错误：

```java
synchronized (lock) {
    while (queue.isEmpty()) {
        lock.wait();
    }
    Task task = queue.poll();
    task.run();   // 长耗时操作，仍持有锁
}
```

后果：

- 其他生产者/消费者全部被挡在锁外，吞吐退化成串行。
- 等待者可能饥饿、超时。
- 如果 `task.run()` 里调用外部代码，或者等待另一个需要同一把锁的线程，就会从性能问题升级为死锁。

正确做法：**锁内只做“检查条件 + 取出/更新必要状态”，锁外做耗时处理。**

```java
Task task;
synchronized (lock) {
    while (queue.isEmpty()) {
        lock.wait();
    }
    task = queue.poll();
}
task.run();   // 锁外执行
```

如果处理结果需要写回共享状态，再单独加锁更新那一小段；不要为了省一次加锁，把整个处理过程包在锁里。

什么时候可以在锁内做工作？工作很短、无阻塞、无外部调用，而且属于维护不变量的必要步骤。判断标准不是“能不能放到锁外”，而是“这段操作是否必须和其他状态变化一起原子完成”。

## 5. 信号量、栅栏、原子类：不是所有同步都要用锁

### 5.1 信号量（Semaphore）

信号量是一个计数器：

- `acquire()`：申请一个许可；没有就阻塞。
- `release()`：归还一个许可，唤醒等待者。
- 初始许可数为 1 时，行为类似互斥锁，但**没有所有权**：任何线程都可以 release。

用途：

- **限流/限并发**：最多 10 个线程同时访问数据库。
- **资源池**：连接池、对象池。
- **信号/事件**：一个线程 release，另一个线程 acquire 后继续。
- **生产者-消费者容量控制**：用两个信号量（空槽数、满槽数）。

示例：限制并发数。

```java
Semaphore permits = new Semaphore(10);

void handle() throws InterruptedException {
    permits.acquire();
    try {
        // 最多 10 个线程同时在这里
    } finally {
        permits.release();
    }
}
```

坑：

- `acquire` 后异常路径忘记 `release` → 许可泄漏，最终所有线程卡死。
- 公平性：默认非公平，可能饥饿；需要时用 `new Semaphore(n, true)`。
- 信号量不保护不变量，它只控制“同时有多少个”。

### 5.2 CountDownLatch / CyclicBarrier / Phaser

| 工具                    | 语义                      | 一次性？ | 典型用途                    |
| ----------------------- | ------------------------- | -------- | --------------------------- |
| `CountDownLatch`        | 等 N 个事件完成           | 是       | 启动信号、等待 N 个任务结束 |
| `CyclicBarrier`         | N 个线程互相等待到齐      | 可复用   | 分阶段并行计算              |
| `Phaser`                | 可动态注册/注销的阶段栅栏 | 可复用   | 复杂多阶段任务              |
| `sync.WaitGroup`（Go）  | 等一组 goroutine 完成     | 是       | 类似 CountDownLatch         |
| `std::barrier`（C++20） | 可复用的栅栏              | 可复用   | 类似 CyclicBarrier          |

`CountDownLatch` 示例：

```java
CountDownLatch start = new CountDownLatch(1);
CountDownLatch done = new CountDownLatch(3);

for (int i = 0; i < 3; i++) {
    new Thread(() -> {
        try {
            start.await();       // 等发令枪
            // do work
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            done.countDown();
        }
    }).start();
}

start.countDown();   // 发令
done.await();        // 等三个线程完成
```

注意：`CountDownLatch` 不能重置；`CyclicBarrier` 可以复用，但一个线程超时/中断会让屏障进入 broken 状态。

### 5.3 原子类与 CAS

原子类保证**单个变量**的读-改-写是原子的，并提供可见性/有序性。

```java
AtomicInteger count = new AtomicInteger();

count.incrementAndGet();
count.compareAndSet(expected, update);
```

```cpp
std::atomic<int> count{0};
count.fetch_add(1);
count.compare_exchange_strong(expected, desired);
```

```go
var count atomic.Int64
count.Add(1)
count.CompareAndSwap(old, new)
```

适用：

- 计数器、序号生成、状态标志、单变量的 CAS 状态机。
- 高并发统计用 `LongAdder`（Java）减少竞争。

不适用：

- 多个变量必须一起变化（转账、库存 + 流水）。
- 需要等待条件（用条件变量/阻塞队列）。
- 复杂的不变量（用锁）。

CAS 的 ABA 问题、内存序、无锁队列是阶段 6 的内容，这里先会用 `AtomicInteger`/`atomic` 即可。

### 5.4 工具选择速查

```text
要保护多变量/复合不变量？
├─ 是 → 用锁
│        └─ 需要等待条件 → 锁 + 条件变量
├─ 否 → 只是单变量读改写？
│        ├─ 是 → 原子类/CAS
│        └─ 否 → 需要限制并发/资源许可？
│                 ├─ 是 → 信号量
│                 └─ 否 → 需要等 N 个事件/阶段同步？
│                          ├─ 一次性 → CountDownLatch
│                          └─ 可复用 → CyclicBarrier/Phaser
```

## 6. 加锁纪律：顺序、粒度、异常与开放调用

这一节是工程中最容易出错的地方。可以把下面 10 条当作 code review 清单。

### 6.1 同一把锁保护同一份状态

- 所有读写路径必须使用同一个锁对象。
- 不要混用 `this`、`Class`、私有锁。
- 不要一部分方法用 `synchronized`，另一部分用 `ReentrantLock`。
- 不要暴露内部锁给外部代码（锁泄漏）。

### 6.2 锁对象的选择

```java
private final Object lock = new Object();   // 推荐：私有、专用、final
```

不要锁：

- `String` 字面量/`intern()` 字符串：全局共享，可能和无关代码互斥。
- `Integer`/`Long` 等包装类型：缓存对象可能被共享。
- `this`：如果对象被外部持有，外部代码也可能锁它。
- `Class` 对象：全局可见，容易被其他代码锁。

### 6.3 覆盖完整操作

检查 + 修改 + 写回必须在同一个临界区。典型错误：

```java
if (!queue.isEmpty()) {          // 检查在锁外
    synchronized (lock) {
        queue.poll();            // 可能已被其他线程取空
    }
}
```

### 6.4 固定加锁顺序

多把锁时，给锁定义全局顺序（如按账户 id、按锁的编号），所有线程按同一顺序获取。

```java
void transfer(Account a, Account b, int amount) {
    Account first = a.id < b.id ? a : b;
    Account second = a.id < b.id ? b : a;
    synchronized (first) {
        synchronized (second) {
            // 转账
        }
    }
}
```

或者用 `tryLock` 带超时，失败就释放已持有的锁并重试/报错。

### 6.5 持锁不调用外部代码

持锁期间不要：

- 调用 RPC、HTTP、数据库、消息队列。
- 调用回调、事件监听器、观察者。
- 调用可能被覆盖的方法（子类可能加锁/阻塞）。
- 做长计算、等待 I/O、`sleep`。
- 获取另一把可能被其他线程以相反顺序持有的锁。

原因：

- 外部代码可能很慢，临界区变长，吞吐下降。
- 外部代码可能回调回来，造成死锁。
- 外部代码可能抛异常，导致锁未释放（Java 的 `synchronized` 会自动释放，`ReentrantLock` 不会）。

正确做法：**开放调用（open call）**——在锁内只修改状态、复制必要数据，释放锁后再做外部调用。

```java
// 锁内取数据，锁外发通知
List<Listener> toNotify;
synchronized (lock) {
    state = newState;
    toNotify = new ArrayList<>(listeners);
}
for (Listener l : toNotify) {
    l.onStateChanged(newState);   // 锁外回调
}
```

### 6.6 异常安全

- Java `synchronized`：异常自动释放锁。
- Java `ReentrantLock`：必须 `try/finally`。
- C++：用 RAII（`lock_guard`/`unique_lock`），不要手动 `lock/unlock`。
- Go：`defer mu.Unlock()`。

### 6.7 锁粒度：先粗后细

- 先用一把锁保证正确，压测后再拆分。
- 拆分前确认不变量可独立；拆分后重新检查跨不变量的操作。
- 不要为了“减少锁竞争”把锁拆得七零八落，最后不变量保护不住。

### 6.8 公平性

- 非公平锁吞吐更高，但可能饥饿。
- 公平锁（`new ReentrantLock(true)`、`new Semaphore(n, true)`）按等待顺序授予，开销更大。
- 只有确实需要“先到先得”或避免饥饿时才用公平锁。

### 6.9 可重入性

- Java 的 `synchronized`/`ReentrantLock` 可重入；C++ `std::mutex`、Go `sync.Mutex` 不可重入。
- 可重入会掩盖设计问题：同一线程重复加锁看起来没事，但锁的边界已经不清晰。
- 避免在持锁时调用可被子类覆盖的方法；子类可能获取另一把锁，导致死锁。

### 6.10 读写锁的取舍

- 读读并发、读写互斥、写写互斥。
- 适合读多写少、读操作不短、写操作不频繁的场景。
- 不一定比互斥锁快：读写锁本身有开销，写者可能饥饿，缓存行竞争仍然存在。
- 先测量，再决定。

## 7. 安全发布、不可变与线程封闭

### 7.1 安全发布

“发布”是把一个对象的引用暴露给其他线程。安全发布保证：其他线程看到引用时，对象已经正确构造，且构造过程中的写对它可见。

Java 的安全发布方式：

- 静态初始化器（`static final` 字段）。
- `final` 字段（正确构造的对象，final 字段对其他线程可见）。
- `volatile` 字段或 `AtomicReference`。
- 锁保护的发布。
- 并发容器（`ConcurrentHashMap` 的 put/get 提供安全发布）。

不安全的方式：

- 把对象引用赋给普通字段，没有同步。
- 在构造函数里启动线程、注册监听器、调用可覆盖方法，导致 `this` 逸出。
- 把 `this` 传给外部方法。

### 7.2 不可变对象

不可变对象一旦构造完成就不能修改，因此可以自由共享。

要点：

- 所有字段 `final`（Java）/ `const`（C++）。
- 不提供 setter；构造时完成全部初始化。
- 对可变的输入/输出做防御性拷贝。
- 不要泄露内部可变集合的引用（`Collections.unmodifiableList` 是视图，不是快照；用 `List.copyOf` 做快照）。

例子：`String`、`Integer`、`LocalDate`、`DateTimeFormatter` 是不可变的；`SimpleDateFormat` 不是，不能共享。

### 7.3 线程封闭

- **栈封闭**：局部变量只在当前线程的栈上，天然安全。
- **ThreadLocal**：每个线程一份副本，适合上下文、非线程安全的工具类。
- **每线程一个对象**：如每个请求一个 `SimpleDateFormat`。

ThreadLocal 的坑：

- 线程池复用线程 → ThreadLocal 不清洗会串数据。
- 必须在 `finally` 里 `remove()`。
- `InheritableThreadLocal` 在线程池里不按预期传播；需要显式传递上下文或使用任务包装。
- ThreadLocal 容易变成隐藏的全局变量，优先用显式参数。

```java
private static final ThreadLocal<SimpleDateFormat> FMT =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

try {
    FMT.get().format(date);
} finally {
    FMT.remove();
}
```

C++ 的 `thread_local` 类似，但同样要小心线程池复用和生命周期。

### 7.4 线程安全组件的组合不一定安全

即使每个组件都是线程安全的，组合操作仍可能有竞态：

```java
ConcurrentHashMap<String, Integer> map = ...;
if (!map.containsKey(k)) {     // 两个原子方法
    map.put(k, 1);             // 组合起来不是原子操作
}
```

解决：用 `computeIfAbsent`、锁、或数据库唯一约束。

## 8. 死锁、活锁、饥饿：从四条件到工程实践

### 8.1 死锁预防

- **固定锁顺序**：最常用。
- **超时/退避**：`tryLock(timeout)`，失败释放已持有的锁。
- **减少锁数量**：能用一把锁就用一把。
- **开放调用**：持锁不调用外部代码。
- **资源分级**：连接池、线程池、锁的顺序也要统一。
- **一次性申请**：`std::scoped_lock` / `std::lock` 可以一次锁多把，内部避免死锁。

### 8.2 死锁排查

- Java：`jstack <pid>`，搜索 "Found one Java-level deadlock"；`ThreadMXBean.findDeadlockedThreads()`。
- C++：`pstack <pid>` / `gdb`，看线程栈和持有的锁；TSan 能检测部分锁顺序反转。
- Go：向进程发送 `SIGQUIT`，看所有 goroutine 栈；运行时会对“所有 goroutine 都阻塞”报 deadlock。

### 8.3 活锁与饥饿

- **活锁**：线程都在运行，但互相让步/重试，没人能前进。解决：随机退避、仲裁者、限制重试。
- **饥饿**：某个线程长期拿不到锁/CPU/资源。解决：公平锁、优先级老化、限制高优先级任务。
- **锁护航（lock convoy）**：大量线程争抢同一把锁，上下文切换和缓存失效导致吞吐崩塌。解决：缩小临界区、拆分锁、用原子类/无锁、批量处理。

### 8.4 线程池饥饿死锁（预览）

一个任务提交子任务到同一个有界线程池，然后同步等待子任务结果。如果池被父任务占满，子任务永远排不上，父任务永远等不到。阶段 4 会展开；现在记住：**不要在池内同步等待同一个池里的任务。**

## 10. 常见误区

- “`synchronized` 方法就线程安全”——只有所有访问路径用同一把锁、且覆盖完整不变量时才成立。
- “锁 `this`/`String`/`Integer` 没问题”——这些对象可能被外部共享，导致意外互斥或死锁。
- “`volatile` 可以替代锁”——它不保证复合操作的原子性。
- “`wait` 用 `if` 就行”——虚假唤醒、多谓词、唤醒后状态变化都会让 `if` 失效。
- “先 `notify` 再改状态”——会丢失唤醒。
- “`wait` 和 `notify` 可以用不同的锁”——必须同一把锁。
- “`notifyAll` 永远比 `notify` 好”——多谓词时 `notifyAll` 更安全，但用两个条件变量更精确；单谓词时 `notify` 足够。
- “`ReentrantLock` 一定比 `synchronized` 好”——它更灵活，但要手动 `unlock`，更容易出错；按需选择。
- “读写锁一定更快”——有开销，写者可能饥饿；先测量。
- “ThreadLocal 没有成本”——不清理会泄漏、串数据。
- “持锁做 RPC/回调没关系”——死锁和长临界区的常见来源。
- “`ConcurrentHashMap` 让组合操作也原子”——不，组合操作仍需额外同步。

## 11. 自测四问

学完后先不看讲义，自己写一遍答案；然后再让我在对话里提问。

### 1. 这把锁保护的不变量是什么？能否用一句话说清？

我的答案：不变量是在多线程操作过程中，需要始终保证遵循的原则。

**点评**

- **结论**：定义方向对，但答成了“不变量的一般定义”，没有回答“这把锁保护的具体不变量是什么”。
- **对的地方**：“多线程操作过程中始终要保证”这个方向没错。
- **需要补**：不变量必须是一个可检查的具体命题，最好能用一句话写出来，并指出临界区覆盖了哪些操作。例如：
  - 转账：两个账户余额之和不变，且每个余额 ≥ 0；临界区同时覆盖扣款和入账。
  - 有界队列：`0 <= size <= capacity`，且 `head/tail/size` 三者一致。
  - 计数器：`count` 始终等于已经生效的 increment 次数。
- **再深一点**：不变量不只是“某个值不能为负”，也可以是“状态与操作历史的关系”（计数器的例子）。写不出具体命题，就说明还没想清楚锁该保护什么。
- **一句话改进**：“这把锁保护的是 X 关系：……；临界区必须覆盖……的完整操作。”

### 2. 多把锁如何确定加锁顺序？

我的答案：按照固定的顺序加锁，或者设置tryLock超时时间，超时自动释放。

**点评**

- **结论**：方向正确，两个主要手段都提到了，但细节不够，而且“超时自动释放”这个说法不准确。
- **对的地方**：固定顺序、`tryLock` 超时都是避免死锁的常用手段。
- **需要补 1：顺序怎么定**。不是泛泛地说“固定”，而是给所有锁一个全局顺序，例如按账户 id 升序、按锁的层级编号，所有线程都按同一顺序获取。只在一处固定、另一处反着来，等于没固定。
- **需要补 2：`tryLock` 失败后怎么办**。`tryLock(timeout)` 超时只是“这次没拿到”，**不会自动释放你已经持有的锁**。你必须自己释放已持有的锁，再退避/重试或报错；否则已经持有的锁会继续阻塞别人。
- **还可以补**：减少锁数量、避免持锁调用外部代码；C++ 可以用 `std::scoped_lock`/`std::lock` 一次性加多把锁。
- **一句话改进**：“给所有锁定义全局顺序（如按 id 升序），所有线程按同一顺序获取；必须嵌套时用 `tryLock` 超时，失败就释放已持有的锁并退避重试。”

### 3. `wait` 为什么必须放在 `while` 循环里？

我的答案：while的条件即使不成立，也会有wait返回的情况，如果wait不放在while而是if里，就无法继续判断是否满足条件。比如，jvm有时会让wait自动返回，或者多个线程同时被唤醒，其中一个进入执行状态改变了条件，其它被唤醒的线程，需要重新判断条件不成立才能继续wait

**点评**

- **结论**：核心原因说对了，尤其是“被唤醒后条件可能已经变了”这一点。术语和完整性可以再补。
- **对的地方**：虚假唤醒、多个线程被唤醒后只有一个能继续、其他人必须重新检查——这些都是 `while` 的理由。
- **需要修正表述**：“while 的条件即使不成立，也会有 wait 返回”建议改成“条件不成立时，`wait` 也可能返回（虚假唤醒）”。`wait` 返回只代表“被唤醒”，不代表“条件成立”。
- **需要补 1：锁重新获取的窗口**。`wait` 返回前要重新拿到锁；从被唤醒到重新拿到锁之间，其他线程可能已经改变了状态，所以必须重新检查。
- **需要补 2：丢失唤醒**。如果 `notify` 发生在 `wait` 之前，`while` 的检查能让你在睡下去之前发现条件已经成立，避免永久等待。
- **需要补 3：多谓词**。多个等待者等待不同条件时，`notifyAll` 会把所有人都唤醒，但只有一部分人的条件成立；其他人必须继续等。
- **一句话改进**：“`wait` 返回只代表可能有机会了，不代表条件成立；虚假唤醒、多谓词、唤醒后状态再变、notify 早于 wait，都要求用 `while` 重新检查谓词。”

### 4. 锁内为什么不能调外部代码？

我的答案：有些外部代码，比如数据库请求，网络请求等，时间很长，会导致线程占用锁的时间过长，降低并发效率；外部代码可能也会上锁，容易发生死锁等情况。

**点评**

- **结论**：两个主要原因都说到了：临界区过长、外部代码可能加锁导致死锁。方向正确，可以再补“回调重入”和“异常安全”。
- **对的地方**：数据库/网络请求很慢，持锁会降低并发；外部代码可能获取其他锁，形成锁顺序环。
- **需要补 1：死锁的具体机制**。不只是“外部代码也上锁”，而是它可能以相反顺序获取锁，或者回调你的对象再拿同一把锁，形成等待环。
- **需要补 2：回调/重入**。外部代码可能回调你的事件监听器、`hashCode`/`equals`、用户提供的 `Comparator`，在你持锁时重新进入你的临界区，看到半更新状态，或者和非可重入锁自死锁。
- **需要补 3：异常与阻塞**。外部代码可能抛异常、永久阻塞；`ReentrantLock` 没写 `finally` 会泄漏锁；`synchronized` 虽然会自动释放，但线程可能已经被卡住。
- **正确做法**：开放调用——锁内只改状态、复制必要数据，释放锁后再调用外部代码。
- **一句话改进**：“外部代码不可控：慢、会加锁、会回调、会抛异常；持锁调用会把临界区拉长，并可能通过锁顺序反转或回调重入造成死锁。锁内取快照，锁外调用。”

### 总评

- 四题都答到了核心方向，说明阶段 2 的主线已经建立。
- 最需要补的是“具体化”：第 1 题要能写出具体不变量；第 2 题要能说出顺序怎么定、`tryLock` 失败后怎么收尾；第 3 题要用准确术语并补“丢失唤醒”；第 4 题要能说出死锁的具体机制和开放调用。
- 建议练习：找一个你项目里的锁，用一句话写出它保护的不变量，再检查所有访问路径是否都用同一把锁。

## 12. 本讲小结

如果只能带走 10 句话：

1. 锁保护的是不变量，不是变量；临界区必须覆盖维护不变量的完整操作。
2. 锁提供互斥、可见性、有序性；但前提是同一把锁、覆盖完整、所有访问者遵守协议。
3. 条件变量解决“在锁的保护下等待条件”，`wait` 必须放在 `while` 里。
4. 先改状态，再 `notify`；多谓词用 `notifyAll` 或两个条件变量。
5. 信号量管“同时多少个”，原子类管“单个变量的读改写”，锁管“多变量的复合不变量”。
6. 多把锁必须有全局顺序；持锁不调用外部代码；异常路径必须解锁。
7. 锁对象用私有、专用、`final` 的对象；不要锁 `String`/`Integer`/`this`/`Class`。
8. 安全发布、不可变、线程封闭，是比加锁更根本的解法。
9. 死锁靠锁顺序、超时、开放调用预防；活锁靠退避；饥饿靠公平性。
10. 先保证正确，再优化粒度；所有优化都要有压测数据。
