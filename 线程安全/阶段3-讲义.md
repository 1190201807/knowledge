## 1. 为什么需要内存模型

内存模型是一份**契约**，规定多线程程序中：

- 一个读操作可能看到哪些写操作的结果（可见性）。
- 编译器和 CPU 允许做哪些重排（有序性）。
- 哪些同步操作会建立顺序（happens-before）。

没有它，程序的行为就取决于具体 CPU、编译器版本和优化级别，既不可移植，也无法证明正确。

它主要回答两个问题：

- **可见性**：线程 A 的写，线程 B 什么时候能看到？
- **有序性**：我写的读写顺序，其他线程看到的顺序是什么？

原子性由锁、原子操作、事务负责；内存模型负责这些操作之间的可见性和顺序。

一个典型问题：

```java
// 线程 A
data = 42;
ready = true;

// 线程 B
if (ready) {
    print(data);   // 能读到 42 吗？
}
```

答案由 **happens-before** 决定，不是由“A 先执行还是 B 先执行”的真实时间决定。

## 2. 重排从哪来：编译器、CPU、缓存

不要以为“源码顺序 = 执行顺序”。重排至少来自三层：

| 层级       | 会做什么                                                 | 例子                                      |
| ---------- | -------------------------------------------------------- | ----------------------------------------- |
| 编译器/JIT | 指令调度、把变量缓存到寄存器、删除“多余”的读、重排独立写 | 把 `while (!stop)` 的读提到循环外         |
| CPU        | 乱序执行、store buffer、load buffer、推测执行            | 写先进入 store buffer，其他核心稍后才看到 |
| 内存系统   | 多级缓存、缓存行、失效队列                               | 一个核心的写不立即可见于另一个核心        |

### 2.1 编译器重排

编译器只保证 **as-if-serial**：单线程程序的行为不变。它不保证其他线程看到的顺序和源码一致。

典型优化：

- 把循环里不变的读提到循环外。
- 把变量长期放在寄存器里，不再每次读内存。
- 交换两个独立的写。
- 删除它认为“没人会看到”的写。

所以 `while (!stop)` 可能在 JIT 编译后变成“只读一次 `stop`，然后无限循环”。

### 2.2 CPU 重排与 store buffer

现代 CPU 会乱序执行。一个关键部件是 **store buffer**：

- 写操作先进入 store buffer，稍后才写入缓存/内存。
- 当前核心的后续读可以通过 store-to-load forwarding 看到自己的写。
- 其他核心可能还没看到这个写。

这就是为什么 x86 的 TSO 模型允许 **StoreLoad 重排**：存储后跟加载，对其他核心来说顺序可能反过来。

不同架构的强弱不同：

- **x86 TSO**：比较强，大多数重排不允许，但 StoreLoad 可以通过 store buffer 重排。
- **ARM/POWER**：弱内存模型，允许更多重排。
- **编译器**：无论什么硬件，都可能重排。

所以“在 x86 上跑对了”不是正确性证明。

### 2.3 缓存一致性不等于语言级可见性

MESI 之类的缓存一致性协议保证：对同一缓存行的访问最终会达成一致。但它不保证：

- 写什么时候对其他核心可见。
- 编译器和 CPU 不会重排。
- 其他线程看到的顺序符合你的意图。

语言级可见性需要 **同步操作**（volatile、锁、原子操作、channel 等）来建立 happens-before。

## 3. 顺序一致性与 SC-DRF

### 3.1 顺序一致性（Sequential Consistency）

顺序一致性是最直观的模型：

> 所有线程的操作可以排成一个全局顺序，每个线程的操作按程序顺序出现，每个读看到的是这个顺序中它前面最后一次写。

它很符合直觉，但代价高：硬件和编译器需要限制大量优化。现实中的语言采用更弱的模型，只在你正确同步时提供顺序一致的假象。

### 3.2 SC-DRF

**SC-DRF**（Sequential Consistency for Data-Race-Free programs）：

> 只要程序没有数据竞争，语言就保证它表现得像顺序一致。

- **Java**：正确同步的程序（没有数据竞争）获得 SC 行为。
- **C++/Rust**：无数据竞争的程序获得 SC；有数据竞争是未定义行为。
- **Go**：无数据竞争的程序行为符合内存模型；有数据竞争则行为不可预测。

这条契约的含义是：**一旦有数据竞争，你就失去了语言层面的保证。** 程序可能“跑对”，但那不是正确性，只是巧合。

## 4. happens-before：核心关系与规则

### 4.1 定义

`A happens-before B`（A hb B）表示：

- A 的内存效果对 B 可见。
- A 在 B 之前发生（在内存模型的顺序意义上，不是墙上时钟）。
- 如果 A hb B 且 B hb C，则 A hb C（传递性）。

happens-before 是一个**偏序**，不是全序。两个操作之间可能既没有 A hb B，也没有 B hb A。

如果两个冲突访问（同一变量，至少一个是写）之间没有 hb 关系，就是**数据竞争**。

> 重要：happens-before 不是“谁先执行”的时间戳。它是一个可见性/顺序保证。A hb B 不意味着 A 在真实时间里一定先发生，而是说如果 B 看到了 A 的同步效果，A 之前的写对 B 可见。

### 4.2 Java 的 happens-before 规则

| 规则     | 含义                                           |
| -------- | ---------------------------------------------- |
| 程序顺序 | 同一线程内，前面的操作 hb 后面的操作           |
| 监视器锁 | 解锁 hb 后续对同一把锁的加锁                   |
| volatile | 对 volatile 变量的写 hb 后续对同一变量的读     |
| 线程启动 | `Thread.start()` hb 新线程中的操作             |
| 线程结束 | 线程中的所有操作 hb 另一个线程从 `join()` 返回 |
| 中断     | `interrupt()` hb 被中断线程检测到中断          |
| 传递性   | A hb B，B hb C ⇒ A hb C                        |
| JUC 工具 | 原子类、并发容器、`CountDownLatch` 等建立 hb   |

### 4.3 C++ 的 happens-before

C++ 用三个关系描述：

- **sequenced-before**：同一线程内的顺序。
- **synchronizes-with**：release 存储 → 读取该值的 acquire 加载；mutex 解锁 → 加锁；线程启动/join；fence。
- **happens-before** = sequenced-before + synchronizes-with + 传递性。

### 4.4 Go 的 happens-before

- channel 发送 hb 对应接收完成。
- close channel hb 接收到零值。
- mutex 解锁 hb 加锁。
- `sync.Once` 的 `Do` 返回 hb 其他 `Do` 返回。
- `WaitGroup.Done` hb `Wait` 返回。
- `go` 语句 hb 新 goroutine 开始执行。
- `sync/atomic` 的操作是顺序一致的。

### 4.5 如何推导一段代码的可见性

步骤：

1. 找出所有同步边（volatile 读写、锁、start/join、channel 等）。
2. 在同一线程内按程序顺序连边。
3. 用传递性看“写”到“读”之间有没有路径。
4. 有路径 → 读能看到写；没有路径 → 没有保证，可能是数据竞争。

例子一：volatile 消息传递。

```java
// 线程 A
data = 42;          // (1)
ready = true;       // (2) volatile 写

// 线程 B
if (ready) {        // (3) volatile 读
    print(data);    // (4)
}
```

推导：

- (1) hb (2)：程序顺序。
- (2) hb (3)：volatile 写 → 后续 volatile 读。
- (3) hb (4)：程序顺序。
- 传递性：(1) hb (4)。

所以 B 能看到 `data = 42`。

例子二：锁。

```java
// 线程 A
synchronized (lock) {
    data = 42;
}

// 线程 B
synchronized (lock) {
    print(data);
}
```

A 的解锁 hb B 的加锁；A 的写 hb 解锁；B 的加锁 hb B 的读；传递性 → A 的写 hb B 的读。

例子三：没有同步。

```java
// 线程 A
data = 42;
ready = true;   // 普通写

// 线程 B
if (ready) {
    print(data);   // 可能打印 0
}
```

没有同步边，没有 hb 路径 → 数据竞争，B 可能看到 `ready = true` 但 `data = 0`。

## 5. 内存序：seq_cst、acquire/release、relaxed、fence

C++/Rust 把内存序暴露给程序员。Java 主要通过 `volatile` 和 `VarHandle` 提供类似能力。

### 5.1 五种内存序

| 内存序    | 作用在    | 保证                                      | 典型用途       |
| --------- | --------- | ----------------------------------------- | -------------- |
| `seq_cst` | 读/写/RMW | 全局总顺序，最强                          | 默认选择       |
| `acquire` | 读/RMW    | 后面的读写不能移到它前面；与 release 配对 | 消费者读标志   |
| `release` | 写/RMW    | 前面的读写不能移到它后面；与 acquire 配对 | 生产者发布数据 |
| `acq_rel` | RMW       | 同时具备 acquire 和 release               | 读-改-写       |
| `relaxed` | 读/写/RMW | 只保证原子性和一致性，不建立顺序          | 计数器、统计   |

### 5.2 消息传递模式

```cpp
std::atomic<bool> ready{false};
int data = 0;

// 生产者
data = 42;
ready.store(true, std::memory_order_release);

// 消费者
if (ready.load(std::memory_order_acquire)) {
    assert(data == 42);   // 保证能看到
}
```

- `release` 保证 `data = 42` 不会被重排到 `ready.store` 之后。
- `acquire` 保证 `data` 的读不会被重排到 `ready.load` 之前。
- 两者配对，建立 happens-before。

如果把 `ready` 改成 `relaxed`，就没有这个保证，消费者可能看到 `ready == true` 但 `data == 0`。

### 5.3 fence

`std::atomic_thread_fence` 可以在不带 acquire/release 的原子操作之间建立顺序：

```cpp
// 生产者
data = 42;
std::atomic_thread_fence(std::memory_order_release);
flag.store(true, std::memory_order_relaxed);

// 消费者
if (flag.load(std::memory_order_relaxed)) {
    std::atomic_thread_fence(std::memory_order_acquire);
    assert(data == 42);
}
```

fence 是进阶工具，能用 acquire/release 直接表达时优先用后者。`std::atomic_signal_fence` 只约束编译器，不生成硬件屏障。

### 5.4 Java 的对应物

- `volatile`：读有 acquire 语义，写有 release 语义，并且 volatile 访问之间有一个全序。它不是“所有操作的全局 seq_cst”，但足够表达消息传递。
- `VarHandle`（Java 9+）：`getAcquire`/`setRelease`、`getVolatile`/`setVolatile`、`getOpaque`/`setOpaque`，可以更细地控制。
- 普通 Java 代码优先用 `volatile`、锁和 `java.util.concurrent`，不要手搓内存序。

### 5.5 选择原则

- **默认用 `seq_cst`**。它是 C++/Rust 的默认值，正确性最容易保证。
- 只有在你能量化收益、并能证明正确性时，才降到 acquire/release 或 relaxed。
- `relaxed` 只适合“不需要和其他内存操作建立顺序”的计数、统计等场景。
- 不要为了“显得高级”使用弱内存序；调试成本远高于收益。

## 6. Java 内存模型（JMM）

### 6.1 核心概念

JMM 用一组**动作**描述程序：

- 读/写普通变量。
- volatile 读/写。
- 加锁/解锁。
- 线程启动/结束/中断。

然后定义：

- **程序顺序**：线程内源码顺序。
- **同步顺序**：所有同步动作（volatile、锁、start/join 等）的全序。
- **happens-before**：程序顺序 + 同步边 + 传递性。
- **数据竞争**：两个冲突访问没有 hb 关系。

### 6.2 volatile 的语义

Java 的 `volatile` 提供三件事：

1. **可见性**：volatile 写 hb 后续对同一变量的 volatile 读。
2. **有序性**：volatile 读写不会被重排到彼此之外；volatile 访问之间有一个全序。
3. **单次读写的原子性**：volatile 的 `long`/`double` 读写也是原子的。

它**不提供**：

- 复合操作的原子性。`volatile int count; count++` 仍然会丢更新。
- 对被引用对象内部字段的可见性。`volatile` 只保护引用本身。

```java
volatile boolean ready;
int data;

// 线程 A
data = 42;
ready = true;

// 线程 B
if (ready) {
    print(data);   // 能看到 42
}
```

### 6.3 锁与 synchronized

- 互斥：同一时刻只有一个线程持有监视器。
- 可见性/有序性：解锁 hb 后续对同一监视器的加锁。
- 临界区内的所有写，对下一个拿到锁的线程可见。

所以锁同时解决原子性、可见性、有序性。

### 6.4 final 字段

`final` 字段在构造器结束时“冻结”。只要对象在构造期间没有逸出：

- 看到对象引用的线程，能看到 `final` 字段的正确初始化值。
- 即使引用是通过普通字段发布的，`final` 字段的初始化安全仍然有保证。

但注意：

- `final` 不保证引用本身被及时/安全地发布。
- `final` 不意味着对象不可变。如果 `final` 字段指向一个可变对象，那个对象仍然可以被修改。
- 如果 `this` 在构造期间逸出，`final` 的保证可能被破坏。

### 6.5 线程启动、join、中断

1. 对线程对象 `t` 调用 `t.start()` 这个动作，hb 线程 `t` 中的第一个动作。

   也就是说：父线程在 `start()` **之前**的写，子线程一定能看到。

   ```java
   int data = 0;
   data = 42;                        // (1) 父线程的写
   Thread t = new Thread(() -> {
       System.out.println(data);     // (2) 子线程的第一个动作
   });
   t.start();                        // (3) 线程启动
   ```

   (1) hb (3)（程序顺序），(3) hb (2)（启动规则），传递性 ⇒ (1) hb (2)：子线程保证打印 `42`，`data` 不需要 `volatile`。

2. 线程 `t` 中的全部动作，hb 另一个线程从 `t.join()` 成功返回之后的动作。

   也就是说：子线程结束前的所有写，调用 `join()` 的线程在 `join()` 返回后都能看到。方向与上一条相反，一进一出。

   ```java
   int data = 0;
   Thread t = new Thread(() -> {
       data = 42;                    // (1) 子线程的写
   });
   t.start();
   t.join();                         // (2) 阻塞到 t 终止才返回
   System.out.println(data);         // (3) 父线程的读
   ```

   (1) hb (2)（线程结束规则），(2) hb (3)（程序顺序）⇒ (1) hb (3)：保证打印 `42`。

   注意：必须是 `join()` **成功返回**（线程确实已终止）。超时返回要再查 `t.isAlive()`，若还存活则没有这条 hb 边。

3. `interrupt()` hb 被中断线程检测到中断（抛 `InterruptedException` 或 `isInterrupted()` 返回 true）。

### 6.6 java.util.concurrent

JUC 的工具都建立了 hb：

- `AtomicInteger`/`AtomicReference` 的原子操作。
- `ConcurrentHashMap` 的 put/get。
- `CountDownLatch.countDown()` hb `await()` 返回。
- `BlockingQueue` 的 put/take。
- `ExecutorService.submit()` hb 任务开始执行；任务完成 hb `Future.get()` 返回。

### 6.7 JMM 的结论

- 没有数据竞争的程序：表现为顺序一致。
- 有数据竞争的程序：可能看到旧值、意外值；JMM 不保证 SC。
- 所以“正确同步”不是可选项，而是获得语言保证的前提。

## 7. C++ 内存模型

### 7.1 基本规则

- C++11 引入正式内存模型。
- **数据竞争是未定义行为**（UB）。不是“可能读到旧值”，而是整个程序的行为都失去保证。
- `std::atomic<T>` 提供原子操作和内存序。
- `std::mutex`、`std::condition_variable`、`std::thread`、`std::future` 等建立同步。
- `volatile` 不是线程同步工具，只用于 MMIO、信号处理等特殊场景。

### 7.2 std::atomic

```cpp
std::atomic<int> counter{0};

counter.fetch_add(1);                       // 默认 seq_cst
counter.store(1, std::memory_order_release);
int v = counter.load(std::memory_order_acquire);
```

- 默认内存序是 `seq_cst`。
- `is_lock_free()` 可以检查是否无锁。
- `std::atomic_flag` 可以实现自旋锁，但通常不推荐手写。

### 7.3 锁与 RAII

```cpp
std::mutex m;
int data = 0;

void writer() {
    std::lock_guard<std::mutex> lk(m);
    data = 42;
}

void reader() {
    std::lock_guard<std::mutex> lk(m);
    assert(data == 42);
}
```

解锁 synchronizes-with 后续加锁，所以 `data` 的写对读者可见。

### 7.4 一次性初始化

```cpp
std::once_flag flag;
Singleton* instance = nullptr;

Singleton* getInstance() {
    std::call_once(flag, [] {
        instance = new Singleton();
    });
    return instance;
}
```

C++11 起，函数内静态局部变量的初始化是线程安全的（Meyers singleton）：

```cpp
Singleton& getInstance() {
    static Singleton instance;
    return instance;
}
```

### 7.5 原子指针的 DCL

```cpp
std::atomic<Singleton*> instance{nullptr};
std::mutex m;

Singleton* getInstance() {
    Singleton* p = instance.load(std::memory_order_acquire);
    if (!p) {
        std::lock_guard<std::mutex> lk(m);
        p = instance.load(std::memory_order_relaxed);
        if (!p) {
            p = new Singleton();
            instance.store(p, std::memory_order_release);
        }
    }
    return p;
}
```

- 外层 acquire 读、内层 relaxed 读、release 写。
- 更简单的做法是 `std::call_once` 或 Meyers singleton。

### 7.6 volatile vs atomic

|             | `volatile`      | `std::atomic`                  |
| ----------- | --------------- | ------------------------------ |
| 原子性      | 不保证复合操作  | 保证该变量的原子操作           |
| 可见性/顺序 | 不建立线程间 hb | 可建立 acquire/release/seq_cst |
| 用途        | MMIO、信号处理  | 线程间同步                     |
| 编译器优化  | 阻止部分优化    | 由内存序控制                   |

**不要用 C++ 的 `volatile` 做线程同步。**

## 8. Go 内存模型

### 8.1 基本规则

- goroutine 共享内存，channel 是主要的同步手段。
- 数据竞争的行为不可预测；用 `go run -race`/`go test -race` 检测。
- `sync/atomic` 的操作是顺序一致的（Go 1.19+）。

### 8.2 happens-before 规则

- channel 发送 hb 对应接收完成。
- close channel hb 接收到零值。
- mutex 解锁 hb 加锁。
- `sync.Once` 的 `Do` 返回 hb 其他 `Do` 返回。
- `WaitGroup.Done` hb `Wait` 返回。
- `go` 语句 hb 新 goroutine 开始执行。
- 原子操作是顺序一致的。

### 8.3 例子

用原子变量做消息传递：

```go
var ready atomic.Bool
var data int

// 生产者
data = 42
ready.Store(true)

// 消费者
for !ready.Load() {
}
fmt.Println(data)   // 保证看到 42
```

用普通 `bool` 就是数据竞争：

```go
var ready bool   // 错误：没有同步

// 生产者
data = 42
ready = true

// 消费者
for !ready {
}
fmt.Println(data)   // 可能打印 0
```

用 channel 传递：

```go
ch := make(chan int, 1)
go func() {
    data := 42
    ch <- data   // 发送 hb 接收
}()
fmt.Println(<-ch)
```

### 8.4 一次性初始化

```go
var once sync.Once
var instance *Singleton

func getInstance() *Singleton {
    once.Do(func() {
        instance = new(Singleton)
    })
    return instance
}
```

Go 没有 `final` 字段；用 `sync.Once`、channel、不可变值来保证初始化安全。

## 9. Rust 内存模型

### 9.1 所有权与 Send/Sync

- `Send`：值的所有权可以跨线程转移。
- `Sync`：`&T` 可以跨线程共享。
- 安全 Rust 在编译期阻止数据竞争；数据竞争只可能出现在 `unsafe` 代码中，且是 UB。

### 9.2 常用工具

```rust
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::{Arc, Mutex};

let counter = Arc::new(Mutex::new(0));
let handles: Vec<_> = (0..10)
    .map(|_| {
        let c = Arc::clone(&counter);
        std::thread::spawn(move || {
            *c.lock().unwrap() += 1;
        })
    })
    .collect();

for h in handles {
    h.join().unwrap();
}
```

- `Arc<Mutex<T>>`：共享所有权 + 互斥。
- `RwLock`：读写锁。
- `AtomicBool`/`AtomicUsize` 等：原子类型，内存序与 C++ 类似（`Relaxed`/`Acquire`/`Release`/`AcqRel`/`SeqCst`）。
- `OnceLock`：一次性初始化（Rust 1.70+）。
- `std::thread::scope`：作用域线程（Rust 1.63+）。

### 9.3 Rust 不解决的问题

Rust 保证安全代码没有数据竞争，但**不保证**：

- 没有死锁。
- 没有竞态条件（业务层面的 check-then-act 仍然可能错）。
- 没有原子性组合问题（多个原子操作组合起来仍可能不原子）。

所以阶段 0–2 的锁纪律、不变量、死锁预防仍然适用。

## 10. 安全发布与初始化安全

### 10.1 什么是发布

“发布”是把一个对象的引用暴露给其他线程。安全发布保证：

- 其他线程看到引用时，对象已经正确构造。
- 构造过程中的写对该线程可见。

### 10.2 Java 的安全发布方式

- 静态初始化器（`static final`）。
- `final` 字段 + 正确构造（无 `this` 逸出）。
- `volatile` 字段或 `AtomicReference`。
- 锁保护的发布。
- 并发容器（`ConcurrentHashMap` 的 put/get）。
- 不可变对象。

不安全的方式：

- 把引用赋给普通字段，没有同步。
- 在构造器里启动线程、注册监听器、调用可覆盖方法。
- 把 `this` 放进静态集合或传给外部方法。

### 10.3 this 逸出

```java
class Worker {
    private int state;

    Worker() {
        new Thread(() -> {
            System.out.println(state);   // 可能看到 0，而不是构造后的值
        }).start();
    }
}
```

线程在构造器里启动，`state` 可能还没初始化完；`this` 逸出破坏了初始化安全。

其他 `this` 逸出：

- 构造器里注册事件监听器。
- 构造器里调用可被子类覆盖的方法。
- 构造器里把 `this` 传给外部服务。

### 10.4 双检锁（DCL）

错误版本：

```java
class Singleton {
    private static Singleton instance;   // 缺少 volatile

    static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

`new Singleton()` 可以拆成：

1. 分配内存。
2. 初始化字段。
3. 把引用赋给 `instance`。

第 2、3 步可能重排。另一个线程在第一次检查时看到 `instance != null`，就会拿到一个**还没初始化完的对象**。

修复：

```java
private static volatile Singleton instance;
```

`volatile` 的写有 release 语义，读有 acquire 语义，禁止相关重排并保证可见性。

其他写法：

- 静态内部类（holder）：

```java
class Singleton {
    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }
    static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

- 枚举单例。
- `sync.Once` / `std::call_once` / `OnceLock`。

### 10.5 final 字段的保证

Java 的 `final` 字段在构造器结束时冻结。只要对象没有在构造期间逸出：

- 看到对象引用的线程，能看到 `final` 字段的正确值。
- 即使引用是通过普通字段发布的，`final` 字段的初始化安全仍然有保证。

但：

- `final` 不保证引用本身被安全/及时发布。
- `final` 不意味着对象不可变。如果 `final` 字段指向可变对象，那个对象仍然可以被修改。
- `this` 逸出会破坏这个保证。

### 10.6 跨语言对比

| 语言 | 初始化安全工具                                    | 注意                  |
| ---- | ------------------------------------------------- | --------------------- |
| Java | `final` 字段、`volatile`、静态内部类、`enum`      | `final` 不等于不可变  |
| C++  | `std::call_once`、Meyers singleton、`std::atomic` | `volatile` 不用于同步 |
| Go   | `sync.Once`、channel、不可变值                    | 没有 `final`          |
| Rust | `OnceLock`、`Arc`、所有权                         | 安全代码无数据竞争    |

### 10.7 安全发布不等于不可变

安全发布只保证“看到引用时，对象已经正确初始化”。如果对象之后还会被修改，你仍然需要锁/原子操作/不可变设计。安全发布解决的是“初始化可见性”，不是“后续并发修改”。

## 11. 经典模式与反模式

### 11.1 模式

| 目标           | 正确做法                                         |
| -------------- | ------------------------------------------------ |
| 懒加载单例     | volatile DCL / 静态内部类 / `call_once` / `Once` |
| 发布不可变对象 | `final` 字段 + 安全发布                          |
| 停止线程       | `volatile` 标志 + `interrupt`                    |
| 计数器         | `AtomicLong`/`LongAdder`                         |
| 一写多读配置   | `volatile` 引用一个不可变对象                    |
| 初始化一次     | `sync.Once`/`call_once`/`OnceLock`               |
| 线程间传数据   | 锁/原子/消息传递/channel                         |
| 数组元素可见性 | `AtomicIntegerArray`/`AtomicReferenceArray`      |

### 11.2 反模式

- 无 `volatile` 的 DCL。
- `volatile int count; count++`。
- `volatile` 修饰数组引用，却以为元素也 volatile。
- `volatile` 引用一个可变对象，却以为对象字段也安全。
- C++ 用 `volatile` 做线程同步。
- 依赖 x86 的强内存模型。
- 在构造器里发布 `this`。
- 以为 `final` 等于不可变。
- 一个访问路径用锁，另一个访问路径用 volatile，互不配对。
- 用 `sleep` 或“跑几次没出错”证明并发安全。

## 12. 实验

### 实验 1：可见性循环

Java：

```java
class Worker {
    private boolean stop = false;   // 先不加 volatile

    void run() {
        while (!stop) {
            // 空转
        }
        System.out.println("exit");
    }

    void shutdown() {
        stop = true;
    }
}
```

- 线程 A 跑 `run()`，线程 B 睡 1 秒后调 `shutdown()`。
- 先不加 `volatile`，观察 A 是否退出；再加 `volatile` 对比。
- 注意：不加 `volatile` 也可能退出，这本身就是一课——并发 bug 是概率性的。

C++/Go 用 `std::atomic<bool>`/`atomic.Bool`，并用 TSan/race detector 对比普通 `bool` 的数据竞争。

### 实验 2：双检锁

- 写错误版 DCL（无 `volatile`），用多线程压测；用 jcstress 尝试观察半初始化对象。
- 加 `volatile` 修复，再用 jcstress 验证。
- 用静态内部类实现，对比代码和正确性。
- C++ 用 `std::atomic` DCL 和 `std::call_once` 对比。

### 实验 3：acquire/release 发布

C++：

```cpp
std::atomic<bool> ready{false};
int data = 0;

void producer() {
    data = 42;
    ready.store(true, std::memory_order_release);
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
    }
    assert(data == 42);
}
```

- 用 release/acquire 跑 TSan，确认没有报告。
- 把内存序改成 `relaxed`，观察 TSan 报告或断言失败。
- Java 用 `volatile` 或 `VarHandle.setRelease/getAcquire` 做同样的事。

### 实验 4：litmus test

写几个经典 litmus test：

- **MP（message passing）**：生产者写数据 + 标志，消费者读标志 + 数据。
- **SB（store buffering）**：两个线程各写一个变量、读另一个变量。
- **LB（load buffering）**。
- **IRIW（independent reads of independent writes）**。

用 jcstress（Java）、herd7/litmus7（C/C++）或手写循环观察允许的结果。重点不是“跑出某个结果”，而是理解**内存模型允许哪些结果**。

### 实验 5：this 逸出

- 在构造器里启动线程，让线程读一个尚未初始化的字段。
- 观察它读到默认值（0/null）。
- 修复：构造器只做初始化，启动线程放到工厂方法或 `start()` 方法里。

## 13. 常见误区

- “`volatile` 等于原子”：不，它不保证复合操作的原子性。
- “`volatile` 能让所有字段可见”：它只保护该变量本身及其前后的顺序。
- “`synchronized` 只负责互斥”：它还提供可见性和有序性。
- “`final` 字段一定安全”：需要对象没有在构造期间逸出；而且 `final` 不保证引用被安全发布。
- “Java 的 `volatile` 和 C++ 的 `volatile` 一样”：完全不同；C++ 的 `volatile` 不建立线程间 hb。
- “x86 不会重排，所以没问题”：编译器会重排；而且代码要可移植。
- “测试通过就是对的”：数据竞争是概率性的，测试通过只说明没触发。
- “happens-before 是墙上时间”：它是可见性/顺序关系，不是时间戳。
- “数据竞争在 Java 里没事”：Java 有定义，但可能读到旧值/意外值；C++/Rust 是 UB。
- “Rust 能防所有并发 bug”：它防数据竞争，不防死锁、竞态条件和原子性组合问题。
- “`relaxed` 更快，应该多用”：只有在你理解并证明不需要顺序时才用。
- “`volatile` 数组让元素也 volatile”：不，只有引用是 volatile；元素需要 `AtomicIntegerArray` 等。

## 15. 小结

如果只能带走 10 句话：

1. 内存模型规定“读能看到哪些写、允许哪些重排”，是可见性和有序性的契约。
2. 重排来自编译器、CPU 乱序和缓存/store buffer，x86 也不能作为正确性依据。
3. SC-DRF：无数据竞争的程序才享有顺序一致的保证；有数据竞争就失去语言保证。
4. happens-before 是偏序，不是墙上时间；没有 hb 路径的冲突访问就是数据竞争。
5. Java 的 hb 规则：程序顺序、锁、volatile、start/join、中断、传递性、JUC。
6. C++ 的 hb = sequenced-before + synchronizes-with + 传递性；数据竞争是 UB。
7. `volatile` 不保证复合操作原子性；C++ 的 `volatile` 不用于线程同步。
8. acquire/release 配对建立消息传递；默认用 `seq_cst`，弱内存序要有证据。
9. 安全发布保证“看到引用时对象已正确构造”；DCL 需要 `volatile` 或 `call_once`/holder。
10. `final` 提供初始化安全，但不等于不可变；`this` 逸出会破坏它。
